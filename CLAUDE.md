## Project

**ScreenScribe** — a paid service (per-video **and** subscription options — see "Decided: business model" below). A user uploads a recorded presentation/lecture video (commonly `.mov`, but should accept multiple formats). The app processes it into a package they download **once**:

1. Screenshots of each new/distinct slide or screen shown in the video
2. A full transcript of the audio (via a locally-run Whisper — see "Decided: transcription")
3. The original video converted to `.mp4`
4. All three bundled into a single zip, streamed back as the download

**Target users:** initially either healthcare professionals needing documentation for continuing-education (CE) courses, or college students wanting lecture notes/study material — market decision still open.

### Core technical pipeline

1. **Upload & ingest** — **built**: drag-and-drop (`components/UploadDropzone.tsx`) or click-to-browse, `POST /api/sessions` validates it's a video under 2GB, creates a `sessions` row, saves the raw file, enqueues a `pg-boss` job
2. **Transcode** — convert to `.mp4` (**built**: `worker/lib/ffmpeg.ts` → `transcodeToMp4()`, see "Decided: pipeline orchestration" → "ffmpeg wired up")
3. **Scene/slide detection** — detect "new screen" moments and extract a screenshot per slide (**built**: `worker/lib/ffmpeg.ts` → `extractSceneFrames()`, see "Decided: pipeline orchestration" → "Scene detection wired up")
4. **Transcription** — run audio through Whisper to generate a timestamped transcript. **Not built** — whisper.cpp isn't installed; the worker currently writes an honest placeholder `transcript.txt` saying so, rather than faking a transcript
5. **Packaging** — **built**: `worker/index.ts` zips the transcoded video, screenshots, and transcript with `archiver`
6. **Delivery** — **built**: `GET /api/sessions/[id]/download` streams the zip once, atomically claims it first (concurrency-safe against double-download), deletes it after, flips status to `downloaded`. Downloads expire after 1 hour if never claimed — see "Decided: notifications & download window"

### Decided: stack (2026-08-07)

Mirrors healthReference's (`../momsProject`) and patientRecordSystem's (`../patientRecordsSystem`) stack, for consistency across the three Light Patterns apps: **Next.js 16 (App Router) + TypeScript + React 19 + Tailwind CSS v4 + raw SQL via `pg`, no ORM**, one hand-written idempotent `lib/migrate.ts`.

### Decided: business model (2026-08-12)

A **paid service** — **both** per-video and subscription, not one or the other. This is the actual reason storage stays minimal (below): every video/screenshot/transcript kept around is cost that doesn't scale, not just a privacy nice-to-have. **Billing/payment integration is now real** (Stripe, test/sandbox mode — see "Decided: billing" below), not a `plans`/`subscriptions`/`credits` table — everything stays inside the existing `users` + `token_grants` shape.

**Pricing model: token-based, no unlimited tier (2026-08-12)** — superseded the earlier flat $6/video + $15/mo-unlimited pass. **1 token = 1 minute of video processed, rounded up.** Deliberately no unlimited plan: metered usage caps how much load a single account can put on the worker (which is real, finite compute, not infinitely elastic), rather than risking the service being overwhelmed by a few heavy users on a flat-rate plan.

- **Pay as you go: $0.20/token.** Anchored the same way as the original pass — below Rev.com's $0.25/min, still enormous margin over the actual few-cents-per-video compute cost worked out earlier.
- **Subscription: $15/month, 100 tokens included** — buying 100 tokens à la carte would cost $20, so this is a real ~25% discount for committing monthly, without being unlimited.
- **Token estimator on the hero page** (`components/TokenEstimator.tsx`) — a slider (video length in minutes) that computes the token/dollar cost live, client-side, no backend. Explicitly illustrative — there's no upload flow yet to probe a real file's duration; the same 1-token-per-minute math is meant to be reused there once one exists, not replaced.
- Pricing section copy now explicitly ties the token model back to the privacy positioning: no unlimited plan is framed as reliability (not a small-print limitation), and "nothing is stored, nothing trains an AI" is framed as *why* the pricing is plain compute-cost rather than a data-driven business model subsidizing it.
- **Target market still explicitly undecided** (healthcare CE professionals vs. college students, or both) — these numbers are a deliberate middle ground meant to work reasonably for either until there's real signup data, not optimized for one segment.
- **Real Stripe checkout now exists (2026-08-14, see "Decided: billing" below)** — `users.token_balance` and the `token_grants` ledger are money-backed via real (test-mode) purchases and subscription payments, not just an admin-facing bookkeeping tool anymore. **Upload-time enforcement is now built too (2026-08-14, see "Decided: token enforcement & expiry extension")** — a shortage doesn't block an upload outright, `token_balance` can go as low as -100, paid off by the next purchase.

### Decided: admin dashboard (2026-08-14) — built

**`is_admin BOOLEAN`, not a roles/permissions system.** One admin persona (the operator) exists right now, not a team needing different access levels, so a single flag on `users` is enough — no `roles` table, no permission matrix. `app/(app)/admin/page.tsx` is gated on it (`redirect("/dashboard")` if false, checked server-side — the nav link being hidden is a UX nicety, not the actual security boundary), and `POST /api/admin/grant-tokens` re-checks it independently rather than trusting that only an admin could have reached the page.

- **`token_grants` is a ledger, not just a balance.** Every addition to `users.token_balance` — whether a real purchase or an admin comp — gets a row: `tokens`, `amount_cents` (nullable), `source` (free text: `subscription`/`pay_as_you_go`/`admin_grant` so far), `note`. `amount_cents IS NOT NULL` is exactly what separates "money changed hands" from "an admin gave someone tokens for free" — the admin page's revenue total sums only the former, so it can't be inflated by comp grants.
- **Revenue is explicitly labeled seeded/test data, not live.** There's no payment processor connected — the numbers come from `lib/seed.ts`'s fake demo customers (`alice`/`bob`/`carol@example.com`, invented purchase amounts, not collected from anyone), not real transactions. The admin page says so directly rather than presenting a real-looking dollar figure with no such caveat.
- **Granting tokens has no functional effect yet beyond the number itself** — same caveat as the business-model section above. It updates a real balance in a real ledger, but nothing in the upload flow reads `token_balance` to decide whether to allow an upload. Useful now for comping specific people ahead of real billing, not yet a working credit system.
- `lib/seed.ts` marks the dev seed account as admin (so local dev testing sees the tab without needing to log in as the real admin account) and separately, `admin@lightpatternsonline.com` was marked admin via a one-off `UPDATE` (not baked into the generic seed script, since it's account-specific, not schema/dev-environment setup).
- **Verified end-to-end with a real browser**: admin sees the nav link and the seeded revenue/users data (confirmed the $24.00 total matches exactly what the seeded grants sum to, not just "a number appeared"); granting 25 tokens to a seeded user updated their balance from 100 to 125, confirmed both in the UI and directly in the database; a freshly-signed-up non-admin account does **not** see the nav link, gets redirected away from `/admin` on direct navigation, and gets a real `403` hitting the grant-tokens API directly (not just relying on the UI being hidden).
- **The real admin account has real tokens now (2026-08-14)**: granted 500 to `admin@lightpatternsonline.com` through the actual `/api/admin/grant-tokens` endpoint (logged in as the seeded admin, not a raw DB write) — a round default for the operator's own account, trivially adjustable via the admin page itself going forward.

### Decided: account status — pause/revoke (2026-08-14) — built

**`users.account_status`** (`'active'` / `'paused'` / `'revoked'`, plain TEXT default `'active'`, no DB `CHECK` — same convention as `sessions.status`, enforced at the app layer). Both non-active states block access identically today; the two labels exist for the admin's own record-keeping (temporary vs. deliberate) rather than different technical treatment — no reason to build that distinction until it's actually needed.

**The real design problem this required solving: sessions are stateless JWTs, so pausing/revoking someone can't just "delete their session" the way it could with a server-side session store.** A session token stays cryptographically valid for its full 30-day life regardless of what an admin does in the database. The fix: `lib/auth.ts`'s `getCurrentUserId()` — already called by every protected route — now queries `account_status` live on every single call instead of trusting the JWT's signature alone, and treats anything but `'active'` as no session. That's what makes pausing take effect on someone's *very next request*, not just future logins.

- `POST /api/admin/set-account-status` — admin-gated (independently re-checked, same pattern as `grant-tokens`), validates the status against an allow-list, and **refuses to let an admin change their own status** — a deliberate guard against accidental self-lockout (there'd be no way back in without a second admin).
- `app/api/auth/login/route.ts` gives a specific "Your account has been paused"/"...has been revoked" message — but only **after** password verification succeeds, not before. Checking status first would let someone probe whether an email is paused/revoked without knowing the password — its own small user-enumeration leak.
- **A pause is not a logout — the session cookie itself is never touched.** Once reactivated, a previously-paused user's *original* session resumes working immediately, with no fresh login required, because `getCurrentUserId()` simply starts returning their id again. Confirmed this is real, not assumed: paused bob mid-session, confirmed his existing tab got bounced to `/login` on its next navigation, reactivated him, and confirmed that same tab could hit a protected page again without ever re-entering credentials.
- `components/AccountStatusControl.tsx` — a small colored-dot + dropdown per row on `/admin`, disabled (read-only) on the admin's own row rather than just relying on the API's refusal, so the UI doesn't even offer an action that would fail.
- **Verified end-to-end with two simultaneous browser sessions** (one as bob, one as admin) rather than sequentially, to actually prove live invalidation and not just "pausing then logging in again fails": paused bob while his session was live elsewhere → his tab bounced to login on the next request → paused-login attempt showed the specific message → reactivated → his original tab worked again with zero re-login → revoked carol → her login attempt showed the specific revoked message → confirmed the admin self-lockout guard refuses with a `400`.

### Decided: billing (2026-08-14) — built, test/sandbox mode

Real Stripe checkout — a `/billing` page where a logged-in user can buy a fixed token pack (one-time) or subscribe ($15/mo, 100 tokens), using **Stripe Elements embedded in our own UI**, not Stripe Checkout's hosted redirect page. Scope is deliberately payments-only: `users.token_balance` becomes real money-backed, but **uploads are still unmetered** — nothing in `app/api/sessions/route.ts` checks or deducts a balance (a separate future decision: estimate vs. actual duration, insufficient-balance handling, refund-on-failure).

- **Packages**: `stripe` (server SDK), `@stripe/stripe-js` + `@stripe/react-stripe-js` (Elements React bindings).
- **Env vars** (`.env.local`, gitignored): `STRIPE_SECRET_KEY`, `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY` (must keep the `NEXT_PUBLIC_` prefix — that's the only thing that gets it into the client bundle), `STRIPE_WEBHOOK_SECRET` (from `stripe listen` at dev time, not the dashboard), `STRIPE_SUBSCRIPTION_PRICE_ID` (a real recurring $15/mo Price, created once via a direct Stripe API call rather than clicking through the dashboard — no reason to script something used exactly once).
- **Schema** (`lib/migrate.ts`): `users.stripe_customer_id` (unique, nullable — one Customer per user, created lazily on first checkout, not at signup), `stripe_subscription_id`, `stripe_subscription_status` (mirrors Stripe's own `subscription.status` values verbatim, kept in sync by the webhook — not set optimistically by the route that triggered the change), `stripe_cancel_at_period_end` (tracked separately because Stripe's own `status` stays `'active'` through the paid period even after cancellation is requested). `token_grants.stripe_reference` (which PaymentIntent/Invoice produced a grant, nullable — admin comps have nothing to point to). New `stripe_webhook_events` table (`id` = Stripe's `event.id`, the idempotency claim key).
- **Token packs**: `lib/tokenPacks.ts` — 25/50/100/250 tokens at $5/$10/$20/$50 (exactly $0.20/token, matching the marketing page). Single source of truth for both the `/billing` UI and the server-side PaymentIntent amount — **the client only ever sends an opaque `packId`, never a dollar amount**.
- **Routes**: `POST /api/stripe/create-payment-intent` (pack purchase), `create-subscription` (payment_behavior `default_incomplete`, needs `expand: ["latest_invoice.confirmation_secret"]` specifically — **`confirmation_secret` is not populated by a bare `expand: ["latest_invoice"]`, a real gap between the Stripe SDK's TypeScript types and what the API actually returns without the explicit nested expand, caught by inspecting the raw API response directly rather than trusting the type signature**), `cancel-subscription` (graceful — `cancel_at_period_end: true`, keeps access through the already-paid period; DB isn't updated optimistically here, the webhook is the single source of truth, same "don't trust the edge that triggered it" pattern as `account_status`).
- **`POST /api/webhooks/stripe`** — no `getCurrentUserId()` call (Stripe isn't a logged-in user); signature verification against the **raw** body (`await request.text()`, Next.js App Router handlers don't auto-parse) is the only gate. Idempotency claim (`INSERT INTO stripe_webhook_events ... ON CONFLICT DO NOTHING`) happens **inside the same transaction** as the grant it guards, not before it, so a mid-processing crash rolls back both together and Stripe's retry can safely reprocess. Handles `payment_intent.succeeded` (pack grants — **only if `metadata.source === "token_pack"`**, since a subscription's first invoice also fires this same event type via its own underlying PaymentIntent with no such metadata; without the guard the first subscription payment would double-grant alongside `invoice.paid`), `invoice.paid` (subscription grants, fires on both the first payment and every renewal alike — resolves the user via `stripe_customer_id`, not metadata, since customer id is always present on an invoice), and `customer.subscription.updated`/`.deleted` (keeps stored status accurate through cancellation, `past_due`, etc).
- `source` values on new `token_grants` rows: `'pay_as_you_go'` / `'subscription'` — matches the strings already anticipated in this file's own data-model section before this was built, rather than inventing new ones. `app/(app)/admin/page.tsx`'s revenue math (`SUM(amount_cents) WHERE amount_cents IS NOT NULL`) needed zero changes — it already picks up real Stripe grants automatically since it never filtered on `source`.
- **Local dev workflow**: Homebrew's bottle install failed (outdated Xcode, would have needed a from-source build) — installed the Stripe CLI by pulling the prebuilt arm64 binary directly from GitHub releases into `~/.local/bin` instead. `stripe listen --forward-to localhost:3000/api/webhooks/stripe` must run alongside `npm run dev` for webhooks to arrive locally — **use the `--latest`/`-l` flag**, since without it the CLI forwards events shaped for the Stripe *account's* default API version, which was older than what the `stripe` SDK npm package expects by default, and would have handed our webhook handler differently-shaped payloads (e.g. `invoice.subscription` at the top level instead of `invoice.parent.subscription_details.subscription`) than what it was coded against.
- **A real Playwright quirk hit while verifying, worth remembering**: `.fill()` on Stripe's card-number input races with Stripe's own live input-masking and silently truncates the value — real keystroke-by-keystroke typing (`.pressSequentially()`) is required. Separately, a normal Playwright `.click()` on the real "Pay" submit button stopped registering with React's event system once the Payment Element's payment-method accordion was expanded (confirmed by tracing: no `handleSubmit` invocation, no network call, despite the button being visible/enabled/correctly positioned) — a native `.click()` dispatched via `page.evaluate()` works and is what real user clicks resolve to regardless. Neither is an app bug; both are documented workarounds for testing Stripe Elements with Playwright specifically.
- **Verified end-to-end with a real browser and real Stripe test-mode API calls, not mocks**: bought the 100-token pack with test card `4242 4242 4242 4242` → balance +100, a `token_grants` row with the right `tokens`/`amount_cents`/`source`/`stripe_reference`. Subscribed with the same card → `stripe_subscription_status='active'`, balance +100 more (200 total), UI showed "Active" with a cancel option. Canceled → UI showed "Cancels at the end of the current period" (not immediately inactive), confirming the graceful-cancel semantics actually took effect rather than just being coded. **Confirmed webhook idempotency for real** (not just by inspection): captured the actual `evt_...` id of the pack purchase's `payment_intent.succeeded` event, ran `stripe events resend` on it, confirmed the balance and `token_grants` row count were unchanged — the duplicate delivery was a true no-op. Confirmed a request with an invalid `stripe-signature` header is rejected with 400 before touching the database. Cleaned up all test state (canceled the test subscription in Stripe, reset the dev user's balance/customer id, cleared the webhook-events table) afterward.

### Decided: token enforcement & expiry extension (2026-08-14) — built

**Uploads are metered now — with a grace debt, not a hard block.** `1 token = 1 minute of video, rounded up` (matching the math `TokenEstimator.tsx` already displayed on the marketing page). A shortage doesn't refuse an upload outright: `users.token_balance` is allowed to go as low as **-100**, no further — paid off automatically the next time the user buys tokens or their subscription renews. Chosen over a hard block because a small shortfall shouldn't be the thing standing between someone and processing a video they've already recorded.

- **Duration probing**: `lib/ffprobe.ts`'s `probeDurationSeconds()` shells to `ffprobe` (already installed alongside `ffmpeg`), reading **stdout** — unlike `worker/lib/ffmpeg.ts`'s `runFfmpeg`, which reads stderr (ffmpeg's own diagnostic channel; ffprobe's actual output goes to stdout). Runs in the **web app**, not the worker — this is a real, new gap: production would need `ffprobe` on the web app's own container too, beyond the already-documented "worker needs ffmpeg on its Railway container" gap.
- **Charging is atomic**: `lib/tokens.ts`'s `chargeTokens()` does `UPDATE users SET token_balance = token_balance - $cost WHERE id = $1 AND token_balance - $cost >= -100 RETURNING token_balance` — a single conditional UPDATE, not read-then-write, so two near-simultaneous uploads from the same user can't jointly push the balance past the floor (Postgres row-level locking serializes them). A `token_grants` row is inserted alongside it (`tokens` stored **negative**, `source = 'usage_upload'` or `'usage_extend'`, `session_id` set) — keeping the existing "every balance change has a corresponding ledger row" invariant intact rather than special-casing debits.
- **Refunds on failure, with a real idempotency guard.** If the worker's job fails (`worker/index.ts`'s `boss.work` catch block) or the upload route itself fails *after* charging but *before* the job is ever enqueued (its own catch block), `refundUsageCharge()` looks up the `usage_upload` grant for that session and credits it back — but only if no `refund` row already exists for that session. **This guard is load-bearing, not defensive-programming theater**: pg-boss defaults to `retryLimit: 2`, and `processSession()` isn't written to be safely re-entrant (it unconditionally marks `processing` at the top with no check of current status) — without the guard, a retried failed job would refund the same charge twice. Fixed at the source too: `process-session`'s queue now has `retryLimit: 0` explicitly (`createQueue`+`updateQueue`, the latter as a one-time fixup since the queue already existed with the old default). Both fixes were caught by a design-review pass *before* any code was written, not discovered in testing.
- **Extension: pay 50 tokens for one more hour, capped at one use per session** (max 2 hours total). `POST /api/sessions/[id]/extend` — one transaction: an atomic conditional `UPDATE sessions SET expires_at = expires_at + INTERVAL '1 hour', extended = TRUE WHERE ... AND extended = FALSE AND expires_at > NOW()` (covers already-extended/expired/wrong-status/not-yours in one shot) → `chargeTokens()` (same -100 floor) → if the charge fails, `ROLLBACK` undoes the `expires_at` bump too, since nothing committed yet.
- **A real scheduled cleanup sweep now exists**, replacing lazy-only enforcement — see "Decided: notifications & download window" above for what changed there.
- **`worker/lib/tokens.ts`** duplicates `refundUsageCharge()` only (the worker never charges, only refunds) — same deliberate cross-package duplication already used for `email.ts`/`tempStorage.ts`.
- **Verified end-to-end with real uploads and forced failures, not just code review**: a real synthetic 70-second video correctly charged exactly 2 tokens (`ceil(70/60)`). Balance at -99 with a 2-token video correctly rejected ("you need 1 more") with the session marked `failed`, the uploaded file deleted, and **zero** ledger rows — nothing charged for a rejected upload. Balance at -95 with a 2-token video correctly succeeded (debt allowed). **Forced a real worker failure** (temporarily renamed the `ffmpeg` binary off `PATH`) and confirmed exactly one refund row + balance restored — then directly re-invoked the refund logic a second time on the same session and confirmed the idempotency guard no-op'd it, proving the double-refund fix. **Forced a failure between charging and enqueueing** (temporarily made `sendProcessSessionJob` throw) and confirmed the upload route's own catch block refunded correctly, proving the second fix. Extended a session once (balance -50, `expires_at` +1h) → extending again correctly rejected; extending with insufficient balance correctly rejected **and left `expires_at` unchanged**, proving the transaction rollback undoes both parts together, not just the charge. Backdated a `complete` session's `expires_at` and manually triggered the real scheduled-job handler (via `boss.send` to the same queue the worker's `.work()` listens on, not a reimplementation) — confirmed `status` flipped to `expired` and the zip was deleted from disk; confirmed the download route's lazy backstop still independently 410s an expired-but-unswept session.

### Decided: object storage (B2) (2026-08-17) — built

**Backblaze B2 (S3-compatible), replacing the `SHARED_TEMP_DIR` local-disk handoff.** Chosen over standing up a new hosting vendor's storage product — B2 is a well-trodden "S3-compatible upload/download" problem, not a protocol that needed inventing, and its pricing (10GB free, then ~$6/TB/month with cheap egress) costs close to nothing at this app's actual footprint, since objects are deleted within an hour of being written (see "Decided: storage & retention" below — this doesn't change that positioning, it just relocates where the bytes briefly sit). The worker stays a separate Railway service (still needs somewhere to run `ffmpeg`, a genuinely different workload from the web app's request/response cycle) — B2 replaces the internal-HTTP file handoff between the two services, not the two-service architecture itself.

- **Bucket**: `screenScribe`, private, default encryption disabled, Object Lock disabled (Object Lock would actively fight the "delete on schedule" requirement). One scoped application key (`screenScribe`, Read+Write, no expiration, no name-prefix restriction) — not the account master key.
- **Env vars** (`.env.local`, gitignored, both packages): `B2_BUCKET_NAME`, `B2_ENDPOINT` (the S3-compatible endpoint B2 shows on the bucket's details page, e.g. `s3.us-west-004.backblazeb2.com` — the region, `us-west-004`, is parsed out of this string rather than configured separately), `B2_APPLICATION_KEY_ID`, `B2_APPLICATION_KEY`.
- **`lib/b2.ts`** (web app) and **`worker/lib/b2.ts`** (worker) — deliberately duplicated, same convention already used for `email.ts`/`tempStorage.ts` (separate npm packages, no shared import). Both wrap `@aws-sdk/client-s3` with `forcePathStyle: true` (B2 needs path-style addressing, not virtual-hosted). The worker's copy self-loads `.env.local` at its own top (`worker/lib/db.ts`'s already-documented hoisting fix — an importing module can't be assumed to have loaded env vars first); the web app's copy doesn't need to, since Next.js loads `.env.local` before any app code runs.
- **Key layout**: `uploads/<sessionId>/<original filename>` (raw upload, extension-preserving — the worker doesn't know the filename ahead of time, so it lists the prefix to find it, mirroring the old `readdir(uploadDir(sessionId))` lookup), `downloads/<sessionId>.zip` (finished package). No DB column tracks these paths — same reasoning as the old `SHARED_TEMP_DIR` convention this replaced: both are deterministic functions of `sessionId`, nothing to store.
- **Local disk isn't gone, just demoted to each service's own scratch space.** `LOCAL_SCRATCH_DIR` (renamed from `SHARED_TEMP_DIR` — the two services no longer need to agree on a shared directory, or even run on the same machine) is where the web app briefly writes an uploaded file so `ffprobe` (a local binary, needs a real file path) can read its duration before the bytes go to B2, and where the worker downloads B2 objects to before handing local paths to `ffmpeg`/`ffprobe` (same reason — neither shells out against a stream). Both are deleted immediately after their local use, whether B2 has already gotten the bytes or not.
- **Upload route** (`app/api/sessions/route.ts`): probes duration from the local scratch copy *before* uploading anything to B2 — a corrupt/unreadable file is a pre-charge failure that never costs a wasted upload. `putObject()` after a successful probe; the B2 object gets cleaned up (`deleteObject()`) on both remaining failure paths (insufficient balance, job-enqueue failure) — the same "nothing orphaned on failure" standard the local-disk version held itself to.
- **Worker** (`worker/index.ts`): `findUploadKey()` lists the `uploads/<sessionId>/` prefix, downloads to local scratch via a plain `pipeline()` into a write stream, processes exactly as before (transcode, scene detection, placeholder transcript, zip — all still genuinely local-disk operations, B2 doesn't change that part), then **uploads the finished zip via `@aws-sdk/lib-storage`'s `Upload` class**, not a plain `PutObjectCommand` — deliberately, so a multi-hundred-MB zip never has to be buffered whole into worker memory just to compute a `Content-Length` upfront (which a streamed body can't provide). Deletes the `uploads/` B2 object once packaging succeeds, then `rm`s the entire local scratch dir regardless.
- **Download route** (`app/api/sessions/[id]/download/route.ts`): `HeadObjectCommand` for `Content-Length` (replacing `stat()`), `GetObjectCommand` for the stream (replacing `createReadStream()`), same claim-then-serve concurrency pattern as before. **Deletes the B2 object immediately after opening the GetObject stream, before it's piped to the client** — the same "delete right after open" pattern the old POSIX version used, but this was a real behavioral question mark going in: POSIX guarantees an open file descriptor keeps serving bytes after `unlink`, and there's no equivalent documented guarantee for "DELETE while a GET is in flight" against an S3-compatible API. **Verified for real, not assumed**: downloaded a real processed zip through this exact code path, confirmed `Content-Length` matched exactly, confirmed `unzip -t` passed clean with all files intact, and confirmed (via a direct `HeadObjectCommand` check) the object was already gone from the bucket — the DELETE issued right after opening the stream did not truncate it.
- **Scheduled cleanup sweep** (`worker/index.ts`'s `cleanupExpiredSessions()`) now issues a `DeleteObjectCommand` against the B2 zip instead of a local `rm()` — same trigger, same 15-minute cadence, see "Decided: token enforcement & expiry extension" for why this sweep exists at all.
- **Verified end-to-end with a real synthetic video and real B2 API calls, not mocks**: generated a synthetic 10-second 2-scene video with `ffmpeg`, uploaded it through the real `/api/sessions` route, watched the worker log it move through `processing` → `complete`, confirmed via a direct B2 listing that the `uploads/` object was gone and only the `downloads/` zip remained after processing, downloaded it through the real `/api/sessions/[id]/download` route, confirmed the zip's contents directly (`unzip -t` clean, a genuine h264/aac `video.mp4` at the correct 10-second duration, exactly 2 screenshots matching the 2 synthetic scene changes, the honest placeholder transcript), confirmed a second download attempt correctly 410s, and confirmed via another direct B2 listing that the bucket was completely empty afterward — nothing orphaned on either side of the pipeline.

### Decided: rate limiting & password reset (2026-08-14) — built

**Rate limiting is Postgres-backed, not Redis** — same reasoning as choosing `pg-boss` over a new queue infrastructure: reuse what's already in the stack. `rate_limit_attempts (key, action, created_at)` is a plain attempt log; `lib/rateLimit.ts` exports `isRateLimited(key, action, maxAttempts, windowMinutes)` (a windowed `COUNT(*)`) and `recordAttempt(key, action)`. Old rows are pruned by the same scheduled cleanup job from "Decided: token enforcement & expiry extension" (rows older than 24h) — cheap to fold in once that scheduling infrastructure existed anyway, rather than leaving the table to grow forever.

- **Login**: keyed by the lowercased email (not IP — the account itself is the thing being protected, regardless of how many source IPs an attacker uses), checked *before* the `SELECT ... FROM users` so a rate-limited request never touches the table. **5 failed attempts / 15 minutes.** An attempt is recorded on **both** failure branches — no-such-user *and* wrong-password, not just the latter. This matters: recording only on wrong-password would mean a nonexistent email never trips the limiter while a real one eventually does, letting an attacker distinguish real accounts from fake ones by watching for the 429 — reopening exactly the enumeration hole the identical `INVALID_CREDENTIALS` message exists to close. Caught by a design-review pass before shipping, not found in testing. Never recorded on success.
- **Signup**: keyed by client IP (`x-forwarded-for`, best-effort — Railway sets it reliably, not spoof-proof), **10 signups / hour**, recorded once validation passes (not on every malformed request).
- **Forgot-password**: keyed by email, same 5/15-minute shape as login.
- **Password reset**, mirroring the existing email-verification precedent deliberately — the only prior pattern in this codebase for a self-contained-JWT, no-DB-token-table, link-based flow:
  - `lib/auth.ts` gains `createPasswordResetToken`/`verifyPasswordResetToken` — identical shape to `createVerificationToken`/`verifyVerificationToken` but `purpose: "password-reset"` and a **shorter** `PASSWORD_RESET_MAX_AGE = "30m"` (vs. verification's 24h) — a reset link is realistically clicked within minutes if legitimate, and unlike replaying a verification link (harmless), replaying a reset link isn't, so a short window meaningfully shrinks that exposure for free.
  - `lib/email.ts` gains `sendPasswordResetEmail`, mirroring `sendVerificationEmail` exactly (same Resend fetch shape, same non-throwing failure handling).
  - `POST /api/auth/forgot-password` — **always returns `{ ok: true }`** regardless of whether the email exists, same enumeration-avoidance principle as login's generic message; only actually sends if a matching user is found.
  - `POST /api/auth/reset-password` — verifies the token, updates `password_hash`. **On success, also clears any existing login rate-limit lockout for that email** — otherwise someone who just proved account ownership via a real email link could still be locked out of login for up to 15 minutes from their own earlier failed guesses.
  - New pages `app/(marketing)/forgot-password` and `.../reset-password` (reads `?token=`) — **deliberately do not** copy the "redirect away if already logged in" guard from login/signup: a user logged in on one device can legitimately still need to reset a password saved/forgotten on another. Both forms use the uncontrolled-input + `FormData`-at-submit pattern from `LoginForm.tsx`/`SignupForm.tsx` (the established fix for the autofill bug documented under "Decided: auth mechanism"), not `useState`+`value`+`onChange`.
  - **Known, accepted trade-off, not a bug**: a reset token has no server-side single-use tracking, so it's technically replayable within its (now-short) window — same trade-off already accepted for email verification, kept consistent rather than introducing a used-tokens table for this flow alone.
  - **Session invalidation on password change — built (2026-08-14).** `users.password_changed_at` (nullable — `NULL` means never reset, so no session is rejected on that basis) is set on every successful `reset-password`. `getCurrentUserId()` now also compares the session JWT's own `iat` claim against it: any session issued *before* the most recent password change is rejected on its very next request, exactly the same live-invalidation trick `account_status` already uses for pause/revoke — same choke point, same "the async DB state is the source of truth, not the token's signature alone" principle, just keyed on a timestamp comparison instead of a status flag. **Verified with two simultaneous browser contexts** (same technique as the pause/revoke verification): logged in and kept a session open, reset the password from a completely separate, unauthenticated context, confirmed the original still-open session was bounced to `/login` on its next navigation with zero further action in that tab, and confirmed a fresh login with the new password worked normally.
- **Verified end-to-end with real repeated requests, not just reading the code**: 6 rapid wrong-password attempts against a real account → first 5 return 401, 6th returns 429, and a *correct* password on the 6th attempt is still rejected (proves the limiter gates before `verifyPassword` runs at all). 6 rapid attempts against a nonexistent email → **also** 429s by the 6th (proves the enumeration fix — this would never have tripped before the fix). 11 signups from one simulated IP → 11th 429s. 6 forgot-password requests for one email → 6th 429s. Full reset flow with a temporary test-only route (same technique already used for email verification) to fetch a real token: reset succeeded, the old password then failed and the new one worked, a garbage token was cleanly rejected, and a pre-existing login lockout on that email was confirmed cleared immediately after a successful reset. Confirmed `forgot-password` returns `{ok:true}` identically for a real and a fake email. Playwright: the forgot-password form shows its generic success message, the login page has a working "Forgot password?" link, and the reset-password page correctly reads `?token=` from the URL.

### Decided: storage & retention (2026-08-12, refined 2026-08-14)

**Nothing persists long-term.** A user's raw upload and the intermediate work files (transcoded mp4, raw screenshots) are deleted the moment the finished zip is built, whether the job succeeded or failed. There is no persistent object storage (no R2/B2/S3, unlike healthReference/patientRecordSystem).

**One real nuance settled 2026-08-14** (once async job processing meant a job could finish while nobody's watching): the *finished zip* isn't deleted instantly — it has to sit somewhere for a bounded window so notifications work at all. See "Decided: notifications & download window" for the actual number (1 hour) and why. "Ephemeral" means *bounded*, not *instant* — that's the honest version of the original "nothing is kept around" framing now that processing is genuinely asynchronous.

All that persists in Postgres is the lightweight `sessions` row (filename, status, timestamps, `expires_at`) — see "Data model" below.

### Decided: notifications & download window (2026-08-14)

Async job processing (already decided) put "ephemeral, nothing kept around" in real tension with reality: a 30–60 minute job means the file has to exist *somewhere* between "done" and "user comes to get it."

- **Email + in-app, not in-app-only.** A user realistically walks away during processing, not watches a progress bar — email is the primary "come back, it's ready" channel; the queue page (`/sessions`) shows live status (polled every 5s via `components/AutoRefresh.tsx`, not a websocket) for whoever's actually in the app.
- **1-hour download window, now with a paid extension (2026-08-14) and a real scheduled sweep — see "Decided: token enforcement & expiry extension" below.** After `status` flips to `complete`, `expires_at` is set to `NOW() + INTERVAL '1 hour'`. After that, the file is gone and the user has to re-upload and spend tokens again — unless they pay 50 tokens for one extra hour before it expires (capped at one extension per session).
- **Enforcement is no longer lazy-only.** `worker/index.ts` now runs a real `pg-boss`-scheduled sweep every 15 minutes that finds overdue `complete` sessions, deletes their zip, and flips them to `expired`. `GET /api/sessions/[id]/download`'s original lazy check (flip-and-delete at request time) is unchanged and still runs — it's now a backstop for the window between actual expiry and the next sweep, not the sole mechanism.
- **Download is streamed, not buffered into memory (2026-08-14).** `readFile()`+`Buffer` was replaced with `createReadStream()` piped through `Readable.toWeb()` — a multi-hundred-MB zip no longer has to be held whole in server memory to serve it. Discussed with the user first (upload streaming is the harder, riskier half — Next.js's `request.formData()` already buffers the whole multipart body internally, so fixing it means switching transports, not a small tweak — deliberately scoped down to just this half for now). **Deletes the file immediately after opening the read stream, not after the client finishes downloading** — safe on POSIX (this Mac and the Linux Railway target both): an open file descriptor keeps the underlying data readable until the descriptor closes, even after the directory entry is removed, so the stream still delivers every byte. Verified for real, not just by reasoning about POSIX semantics: downloaded a real processed zip, confirmed the file was already gone from disk by the time headers came back, confirmed the downloaded zip passed `unzip -t` with zero errors and all three expected files intact, confirmed `Content-Length` matched exactly, and confirmed one-time-download enforcement (a second attempt correctly 410s) still holds.
- **Email provider: Resend**, called via raw `fetch` to their REST API (`worker/lib/email.ts`) — no SDK dependency needed for one endpoint. **A real API key is configured (2026-08-14)** — `RESEND_API_KEY` in both `.env.local` files (a project-agnostic Light Patterns org key, not one scoped just to ScreenScribe). Verified with a real send: both a raw `curl` to Resend's API and the actual `sendDownloadReadyEmail()` function returned success (`200`, an email id). **Real-world constraint**: no custom domain is verified with Resend yet, so the `onboarding@resend.dev` sender can only deliver to the Resend account owner's own address (`admin@lightpatternsonline.com`) — it will silently not deliver to arbitrary signup emails (like the seeded `dev@screenscribe.test`) until a domain is verified under Resend's "Domains" tab. Don't assume the ready-email actually reaches a real user yet.

### Decided: transcription (2026-08-12)

**Local Whisper only — no cloud transcription API**, regardless of any provider's stated training/retention policy. Users' video content should never leave the machine it's processed on. **whisper.cpp** (C++ port, no Python dependency, Metal-accelerated on Apple Silicon) invoked as a local binary the same way ffmpeg is — fits the existing "shell out to a local tool" shape rather than introducing Python or a persistent model-serving process.

**Model size: `medium`** (2026-08-12) — chosen after working through actual cost/speed numbers, not guessed at:
- Railway bills compute at ~$0.0009/vCPU+2GB-minute. Even the slowest realistic model choice landed around $0.02–0.03 of compute per 30-minute video — marginal transcription cost turned out to not be the pricing bottleneck at all (the fixed monthly cost of keeping a worker running dominates at low volume, not per-video compute). That freed up the model choice to prioritize accuracy over squeezing out the cheapest/fastest option.
- **Must run quantized (e.g. INT4/`q4`-class ggml weights), not full FP16** — benchmark data: FP16 `medium` runs *slower* than real-time on CPU (~1.8×), which would make a 30-minute video take ~54 minutes to transcribe; the quantized variant is faster than real-time (RTF ≈ 0.76, ~23 minutes for the same video). Exact quantization level (`q4_0` vs `q5_0` etc.) not pinned yet — a call to make once whisper.cpp is actually being installed and models compared for accuracy loss, not a business decision.
- Not implemented yet — this is the decided model choice, not working code. No whisper.cpp binary or model file exists on this machine yet.

### Decided: auth mechanism (2026-08-12) — built

**Email + password**, not OAuth or magic-link — keeps credential storage in-house rather than round-tripping logins through a third-party identity provider, consistent with the local-processing-only stance above.

- `lib/auth.ts` — `hashPassword`/`verifyPassword` (`bcryptjs`, 12 rounds), `createSession`/`clearSession`/`getCurrentUserId` (a signed JWT via `jose`, HS256, in an httpOnly cookie — `SESSION_SECRET` in `.env.local`, generated locally, gitignored, **production needs its own**, not the same value). 30-day expiry. `getCurrentUserId()` returns `null` for a missing/expired/tampered cookie rather than throwing — callers treat "no session" and "bad session" identically.
- `app/api/auth/{signup,login,logout}/route.ts` — signup validates email format + 8-char-minimum password, hashes, inserts, and relies on the `users.email` unique constraint (Postgres error `23505`) for the race-safe duplicate check rather than a pre-check `SELECT` (which would have a TOCTOU gap). Login returns the same generic "Invalid email or password" whether the email doesn't exist or the password is wrong — deliberate, avoids user-enumeration.
- **No `middleware.ts`** — auth gating happens in `app/(app)/layout.tsx` (a server component that calls `getCurrentUserId()` and `redirect("/login")` if absent), not Next.js middleware. Keeps the "no middleware" pattern consistent with healthReference/patientRecordSystem rather than introducing a new architectural layer.
- Verified end-to-end with a real browser (Playwright, scratch script, not committed): signup → dashboard, logout → redirected to `/login` on next visit to a protected route, duplicate-email signup shows the 409 error, wrong password shows the generic 401, correct login succeeds, and visiting `/login`/`/signup` while already authenticated redirects to `/dashboard` instead of showing the form again.
- **Password reset and rate limiting are now built (2026-08-14) — see "Decided: rate limiting & password reset" below.**
- **Now actually used beyond the layout gate (2026-08-14)**: `sessions.user_id` is populated by the real upload flow, `app/(app)/sessions/page.tsx` and the dashboard's session count both scope their queries to `getCurrentUserId()`, and the download route checks session ownership before serving anything.
- **`LoginForm`/`SignupForm` inputs are uncontrolled, not React `useState`-controlled (2026-08-14).** Browser autofill sets an input's DOM value without reliably firing the native `input` event a controlled component's `onChange` depends on — a well-documented React/browser interaction issue, not specific to this app, and one that's reportedly gotten more aggressive across browsers recently. Symptom before the fix: autofilled fields visually showed the right value but submitted stale/empty data, fixed only by a real keystroke (typing a character forces the event React needed). Fix: `defaultValue` instead of `value`+`onChange`, `name` attributes added, and `handleSubmit` reads via `new FormData(e.currentTarget)` at submit time instead of trusting component state — this is accurate regardless of *how* the value got into the field (typing, autofill, a password manager), so there's no sync to break. **Verified against the actual failure mode, not just normal typing**: set the input's DOM value directly via the native property setter with zero events dispatched (Playwright's `.fill()` simulates real typing and wouldn't have reproduced the bug), then confirmed the submitted request body still contained the correct values and login succeeded.
- **`first_name`/`last_name` required at signup (2026-08-14)** — unlike `phone`, which stayed optional. Both nullable at the DB level (existing accounts predate the field and there's no real name to backfill them with — guessing would be worse than leaving it blank — `admin@lightpatternsonline.com` and the dev seed account both still show blank), but the signup route rejects a missing/empty first or last name for every new account going forward. `SignupForm` gained two required fields; the three seeded demo customers got realistic names for a truer admin-dashboard demo.

### Decided: email verification (2026-08-14) — built, soft/non-blocking

**Signup still logs the user in immediately, even unverified** — no reason to lock someone out of an account they just created just because a JWT-purpose token check gates access to email. A dismissable-by-verifying banner (`components/VerifyEmailBanner.tsx`, shown from `app/(app)/layout.tsx` whenever `users.email_verified_at IS NULL`) is the actual mechanism, not a login block. Nothing else is gated on verification status yet — uploads work the same either way.

- **No token table.** Verification links use a short-lived (24h) JWT signed with the same `SESSION_SECRET` `lib/auth.ts` already uses for sessions — `createVerificationToken`/`verifyVerificationToken`. Nothing is stored server-side; the signature + a `purpose: "email-verification"` claim + expiry *is* the proof. **Purpose-scoping matters here**: both session and verification tokens share a secret, so `getCurrentUserId()` now also checks `purpose === "session"` explicitly — without that check, a verification-link token could have been replayed as a login session, or vice versa.
- `lib/email.ts` (new, **root** package) — same raw-`fetch`-to-Resend pattern as `worker/lib/email.ts`, deliberately duplicated rather than shared (separate packages, and they send different things: this one's account emails, the worker's is processing-complete).
- `GET /api/auth/verify?token=...` — **no auth check**, intentionally: the token itself is the authorization, and someone might click the link from a different browser/device than they signed up on. Sets `email_verified_at = NOW()` (idempotent — `WHERE email_verified_at IS NULL`), redirects to `/dashboard?verified=success` or `?verified=error`.
- `POST /api/auth/resend-verification` — auth-gated, issues a fresh token, refuses if already verified. **Not rate-limited** — login/signup/forgot-password are (see "Decided: rate limiting & password reset"), but resend-verification requires an active authenticated session already, which is a meaningfully different bar than an anonymous endpoint; not extended here.
- Seeded dev account (`dev@screenscribe.test`) is pre-verified in `lib/seed.ts` — it's a non-routable `.test` address that could never receive a real link, so leaving it unverified would just mean the banner nags forever in local dev for no reason.
- **Verified end-to-end with a real browser and a real send**, not a mock: signed up with `admin@lightpatternsonline.com` (the Resend account owner's own address — the only one the unverified `onboarding@resend.dev` sender can currently reach, see "Decided: notifications & download window"), confirmed the signup response and server logs showed no Resend error (a real send succeeded, silently — the code only logs on the no-op or error paths), confirmed the banner appeared, confirmed the resend button works, then confirmed the actual verify link (fetched via a temporary test-only route, deleted afterward, since there's no inbox access to click a real email) flips `email_verified_at`, makes the banner disappear, and shows a "Email verified — thanks!" message. Also confirmed an invalid/garbage token cleanly shows the error path instead of either silently succeeding or crashing.
- **One real gap this hit while testing, not a hidden one**: `app/api/_test-only/` (leading underscore) is a Next.js *private folder* convention — routes inside are excluded from routing entirely, so the first version of the temp test route 404'd. Renamed to `app/api/test-verify-token/` (no underscore) to actually be reachable, then deleted once testing was done. Worth remembering: **any route folder starting with `_` silently doesn't route** in this app's Next.js version.
- **Known gap, not fixed**: if someone clicks the verify link without an active session (different device), `/dashboard` bounces them to `/login` per the normal auth gate, and the `?verified=success`/`?verified=error` query param doesn't survive that redirect — the verification itself still succeeds (the DB update happens regardless), just the confirmation toast won't show in that specific cross-device path. Not worth the complexity of preserving redirect state across a login bounce right now.

### Decided: pipeline orchestration (2026-08-12)

**A separate background worker service, not a synchronous request handler.** Real videos take minutes to transcode/detect-scenes/transcribe — well past any reasonable HTTP/reverse-proxy timeout, and a held-open request has no way to show progress and loses the job entirely on a server restart.

- **Job queue: `pg-boss`** (Postgres-backed) rather than Redis-backed (BullMQ, etc.) — reuses the Postgres already in the stack instead of adding a second infrastructure dependency. `sessions.status` is the natural place to reflect job progress (free-text column, no schema change needed to add intermediate values like `transcoding`/`detecting_scenes`/`transcribing` later if per-stage progress is wanted).
- **Worker host: a second Railway service**, not a standalone VM (Hetzner/DO/AWS/etc.) — chosen as the starting point specifically to avoid standing up a new hosting vendor, and because it's a platform already known here. It's a plain Linux container, so `whisper.cpp` runs **CPU-only, no Metal acceleration** — meaningfully slower than the Mac dev machine. Revisit a dedicated box (e.g. AWS EC2 Mac instances, for Metal-accelerated `whisper.cpp` in the cloud) only if transcription speed becomes a real problem under actual usage — not a preemptive optimization.

**Repo layout decided:** the worker lives in **this repo**, in a `worker/` directory alongside `app/`, `lib/`, `components/` — deployed as a second Railway service from the same codebase, not split into a separate repo.

**File handoff: real network handoff via B2 now, not a shared filesystem (2026-08-17) — built.** The `SHARED_TEMP_DIR` local-disk trick this section used to describe is gone. See "Decided: object storage (B2)" below for the real design — this actually works once the worker is a separate Railway service, not just in local dev.

**Worker: real pipeline, not a stub (2026-08-14).** `worker/` is a real, separate npm package — its own `package.json`/`tsconfig.json`/`.env.local`, excluded from the root project's `tsconfig.json`/`eslint.config.mjs` (diverging dependency versions, e.g. `@types/node` majors, shouldn't be typechecked/linted as one program). `worker/index.ts`'s `process-session` handler now does the real thing: marks the session `processing`, locates the uploaded file, runs `transcodeToMp4` + `extractSceneFrames`, writes a placeholder `transcript.txt` (whisper.cpp isn't installed), zips everything with `archiver`, marks the session `complete` with a 1-hour `expires_at`, sends (or logs) the ready email, and deletes the upload/work directories either way. **Verified end-to-end with a real browser** (Playwright, scratch script): logged in, uploaded a real synthetic 2-slide test video via the dropzone's file input, watched it move `queued` → `processing` → `complete` in the polling queue UI, downloaded it, and confirmed the unzipped contents directly — genuine h264/aac `video.mp4` at the correct duration, exactly 2 screenshots matching the 2 slides, and the honest placeholder transcript. Also confirmed the one-time-download enforcement: after downloading, the session shows `Downloaded` and the download link disappears from the queue.

**A real bug this surfaced, worth remembering:** `worker/lib/db.ts` originally built its `Pool` at module top-level using `process.env.DATABASE_URL`. That silently broke the first time `worker/index.ts` actually imported it — ES module imports are hoisted, so `lib/db.ts`'s top-level code ran *before* `index.ts`'s own `dotenv.config()` call, meaning `DATABASE_URL` was still `undefined` when the `Pool` was constructed (pg silently fell back to a default connection using the OS username as the database name — `FATAL: database "henrywalton" does not exist`). Fixed by making `lib/db.ts` load its own env vars at its own top, the same self-contained pattern already used in `index.ts` and `lib/migrate.ts` — don't assume an importing module has already loaded `.env.local` by the time your module's top-level code runs.

**ffmpeg (2026-08-12):** `ffmpeg` installed locally via Homebrew (`brew install ffmpeg`, v9.0 — will need the equivalent on whatever the worker's Railway container build ends up being, e.g. a `nixpacks.toml`/Dockerfile `apt-get install ffmpeg` — **not set up yet**). `worker/lib/ffmpeg.ts` exports `transcodeToMp4(inputPath, outputPath)`, shelling out via `child_process.spawn` (argument array, not a shell string) to `libx264`/`aac`/`+faststart` — chosen over Apple's hardware encoder (`videotoolbox`, also available locally) so encoding behaves identically between this Mac and the Linux worker in production. Now actually called from the real job handler (see above), not just tested in isolation.

**Scene detection (2026-08-12):** **ffmpeg's own scene-change score** (`select='eq(n,0)+gt(scene,threshold)'`, `-fps_mode vfr`), not a separate frame-diffing library — reuses the tool already shelled out to for transcode. `eq(n,0)` always keeps the very first frame (the first slide is never a detected "change," confirmed empirically). `worker/lib/ffmpeg.ts` exports `extractSceneFrames(inputPath, outputDir, threshold = 0.3)`; `threshold` still **not tuned against a real slide-deck recording**, only synthetic test content. Now actually called from the real job handler.

### Data model — what exists vs. what's still open (2026-08-12)

`lib/migrate.ts` covers only two tables, deliberately thin given "Decided: storage & retention" above — there's no media to reference, so there's nothing resembling the earlier `screenshots`/`transcript_segments` tables (removed, not just unused):

Needed before ready-emails actually reach anyone but the account owner.
- **Production Stripe.** Everything is test/sandbox mode — no live keys, no live webhook endpoint registered anywhere outside a local `stripe listen` tunnel.
- **`ffprobe` on the web app's production container.** Upload-time duration probing (see "Decided: token enforcement & expiry extension") runs locally today because `ffmpeg`/`ffprobe` are installed on this dev machine and shared between both processes — production would need `ffprobe` installed on the web app's own Railway container too, beyond the already-documented "worker needs ffmpeg" gap.
- **Streaming upload.** The upload route still buffers the whole file into memory (`arrayBuffer()`) before writing — Next.js's `request.formData()` already buffers the full multipart body internally, so fixing this means switching the upload transport away from multipart entirely (a raw-body stream, with metadata like filename passed via headers/query params instead of form fields) rather than a small tweak — touches both this route and `components/UploadDropzone.tsx`. **Download streaming was fixed (2026-08-14)** — see "Decided: notifications & download window" below; discussed and deliberately scoped down to just the download half for now, since it's the lower-risk, server-only change.

### Routing structure (2026-08-12)

Two route groups, each with its own layout — introduced alongside auth since logged-out (marketing) and logged-in (app) pages need different chrome:

- **`app/(marketing)/`** — public, no `Sidebar`. `page.tsx` is the hero/pricing landing page at `/`, plus `login/` and `signup/`. Its layout (`app/(marketing)/layout.tsx`) shows a simple header — "Log in"/"Get Started" links if logged out, a "Dashboard" link if logged in (reads `getCurrentUserId()`, doesn't redirect, just changes what's shown).
- **`app/(app)/`** — `dashboard/` (the tile dashboard, moved here from the old `app/page.tsx`), `sessions/`, `upload/`. Its layout (`app/(app)/layout.tsx`) renders `Sidebar` and redirects to `/login` if there's no session — this is the auth gate, see "Decided: auth mechanism".
- Route groups don't affect the URL — `/dashboard`, `/sessions`, `/upload` are still those exact paths, just nested under `(app)/` in the filesystem for layout purposes.
- Root `app/layout.tsx` is now minimal — just `<html>`/`<body>`/font, no `Sidebar`, since that's specific to `(app)/layout.tsx` now.
- `components/Sidebar.tsx`'s "Home" nav link and brand link now point to `/dashboard` (not `/`, which is the public marketing page now) and it gained a "Log out" button (POSTs to `/api/auth/logout`, then `router.push("/")`).

**Dev login:** `npm run seed` upserts a fixed dev account (`dev@screenscribe.test` / `devpassword123`) via `lib/seed.ts` — log in with it at `/login` instead of signing up fresh every time the local DB gets reset. Dev-only seed data, not a bypass in the auth code itself — deliberately didn't hardcode a special-case credential check into `app/api/auth/login/route.ts`, since that's exactly the kind of thing that's dangerous to leave in security-critical code.

`components/LoginForm.tsx` also pre-fills those credentials, gated on `process.env.NODE_ENV === "development"` — a build-time constant Next.js replaces before bundling (the same mechanism React itself uses to strip its own dev-only code), not a runtime `if` that could be toggled or bypassed. **Verified this is actually stripped, not just hidden**: ran `npm run build`, then grepped the real output (`.next/server`, `.next/static`, excluding `.map` files) for both credential strings — zero matches. They only appear in a server-chunk source map (expected — maps embed original source for debugging, not executable logic, and aren't sent to the browser regardless). Shows a small "Dev mode" note on the form itself so the pre-fill is never mistaken for a real remembered login.

## Commands

Web app (run from repo root):

Worker (separate package — run from `worker/`, not the repo root):

```bash
cd worker
npm install          # Install dependencies (own node_modules, not shared with root)
npm run dev           # Start the worker (tsx watch), connects to DATABASE_URL in worker/.env.local
npx tsc --noEmit      # Type-check
```

**To actually exercise the upload → process → download flow locally**, both need to be running at once (two terminals, or two background processes) — the web app alone can create a session and enqueue a job, but nothing will ever leave `queued` without the worker also running to pick it up. Both must point at the same B2 bucket (`B2_BUCKET_NAME` + credentials in each package's `.env.local` — see "Decided: object storage (B2)"); `LOCAL_SCRATCH_DIR` is local-only now and doesn't need to match between them.
