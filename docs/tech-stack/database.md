# Database

- **Engine:** Postgres (local), database name `screenscribe`
- **Driver:** [`pg`](https://node-postgres.com/) (`node-postgres`), raw SQL — **no ORM**
- **Connection:** `lib/db.ts` — single `Pool` singleton, `connectionString` from `DATABASE_URL` in `.env.local`
- **Migrations:** no migration framework — `lib/migrate.ts` is one hand-written idempotent script (`CREATE TABLE IF NOT EXISTS`). Run with `npm run migrate`.
- **Seeding:** `lib/seed.ts`, run with `npm run seed`. Dev-only: upserts one known user (`dev@screenscribe.test` / `devpassword123`, hashed via `bcryptjs` directly — deliberately doesn't import `lib/auth.ts`, since that file also exports session helpers that touch `next/headers`, which isn't safe to import outside a Next.js request context). Idempotent — re-running just resets the password.

## Tables

Three. See `CLAUDE.md` → "Decided: storage & retention": nothing about a processed video persists *durably*, so there's no media table to design.

- `users` — `id` (UUID PK), `email` (unique), `password_hash`, `created_at`, `email_verified_at` (nullable, `NULL` = unverified), `phone` (nullable, **optional**, no format validation beyond a loose 7–15-digit sanity check — see `CLAUDE.md` → "Decided: email verification" area for why it's optional), `is_admin` (default `false`), `token_balance` (default `0`). Written to by `app/api/auth/signup/route.ts`, read by `app/api/auth/login/route.ts`, by the worker (to find the address for the "ready" email), and by `app/(app)/layout.tsx` (whether to show the verify-email banner, and whether to render the Admin nav link) — email+password auth is built, see `CLAUDE.md` → "Decided: auth mechanism" and "Decided: email verification". Nothing currently reads `phone` — captured for future use, not acted on. `token_balance` is likewise not enforced anywhere (uploads aren't metered) — see `CLAUDE.md` → "Decided: admin dashboard".
- `sessions` — a real lifecycle, not just a log: `id` (UUID PK), `user_id` (FK → `users`, `ON DELETE CASCADE`, `NOT NULL`), `original_filename`, `status` (`queued` / `processing` / `complete` / `downloaded` / `expired` / `failed`, default `'queued'`), `error_message`, `expires_at` (nullable, set to `NOW() + INTERVAL '1 hour'` when a job completes), `created_at`/`updated_at`. Indexed on `user_id`. Still no `video_key`/`image_key` — the actual file lives transiently on disk (`SHARED_TEMP_DIR`, see `architecture.md`), never referenced by a DB column, so there's no persistent pointer to clean up or worry about leaking.
- `token_grants` — `id` (UUID PK), `user_id` (FK → `users`, `ON DELETE CASCADE`, `NOT NULL`), `tokens`, `amount_cents` (nullable — `NULL` distinguishes a comp/admin grant from a real purchase, this is what keeps the admin page's revenue total honest), `source` (free text: `subscription`/`pay_as_you_go`/`admin_grant` so far), `note` (nullable), `created_at`. Indexed on `user_id`. Every change to `users.token_balance` should have a corresponding row here — the balance is a derived running total, the ledger is the source of truth.

## Notable patterns

- `users.email` has a `UNIQUE` constraint that's actually relied on — the signup route inserts directly and catches Postgres error `23505` (unique_violation) rather than doing a pre-check `SELECT` first, which would leave a race window between the check and the insert.
- **`sessions.status` transitions are enforced by `UPDATE ... WHERE status = 'x'` clauses, not application-level locking.** Two places rely on this: the worker's job handler only ever moves a session forward (`queued`→`processing`→`complete`), and the download route's claim step (`UPDATE sessions SET status = 'downloaded' ... WHERE status = 'complete' RETURNING id`) is what makes concurrent double-download attempts safe — if two requests race, only one `UPDATE` actually matches a row.
- `sessions.user_id` is now genuinely used everywhere: the upload route sets it, the dashboard/sessions pages filter by it (`getCurrentUserId()`), the download route checks it before serving anything.
- **Previously had `screenshots` and `transcript_segments` tables** (one row per detected slide, one per transcript segment) — removed 2026-08-12 when the storage model changed from "keep the output, let users re-download" to "one-time download, nothing kept." See `docs/changelogs/2026-08-12.md`.
- `expires_at`, the expanded `status` vocabulary, and (same day) `email_verified_at` were all added via real `ALTER TABLE` statements (2026-08-14) rather than from-scratch rewrites — real user accounts existed in the table by then, unlike earlier schema changes.
- **No verification-token table.** Verification links are self-contained JWTs (signed with `SESSION_SECRET`, same as sessions), not a stored/lookup-able token — see `CLAUDE.md` → "Decided: email verification" for why (and the purpose-scoping that keeps them from being confused with session tokens despite sharing a secret).
