# Database

- **Engine:** Postgres (local), database name `screenscribe`
- **Driver:** [`pg`](https://node-postgres.com/) (`node-postgres`), raw SQL — **no ORM**
- **Connection:** `lib/db.ts` — single `Pool` singleton, `connectionString` from `DATABASE_URL` in `.env.local`
- **Migrations:** no migration framework — `lib/migrate.ts` is one hand-written idempotent script (`CREATE TABLE IF NOT EXISTS`). Run with `npm run migrate`.
- **Seeding:** `lib/seed.ts`, run with `npm run seed`. Dev-only: upserts one known user (`dev@screenscribe.test` / `devpassword123`, hashed via `bcryptjs` directly — deliberately doesn't import `lib/auth.ts`, since that file also exports session helpers that touch `next/headers`, which isn't safe to import outside a Next.js request context). Idempotent — re-running just resets the password.

## Tables

Seven. See `CLAUDE.md` → "Decided: storage & retention": nothing about a processed video persists *durably*, so there's no media table to design.

- `users` — `id` (UUID PK), `email` (unique), `password_hash`, `created_at`, `email_verified_at` (nullable, `NULL` = unverified), `first_name`/`last_name` (nullable at the DB level — existing rows predate the field, no real name to backfill them with — but the signup route requires both for every new account), `phone` (nullable, **optional**, no format validation beyond a loose 7–15-digit sanity check — see `CLAUDE.md` → "Decided: email verification" area for why it's optional), `is_admin` (default `false`), `token_balance` (default `0`, can go negative down to -100 — see `CLAUDE.md` → "Decided: token enforcement & expiry extension"), `account_status` (default `'active'`, `'paused'`/`'revoked'` otherwise — plain TEXT, no DB `CHECK` constraint, enforced at the app layer; checked live on every request via `getCurrentUserId()`, not just at login — see `CLAUDE.md` "Decided: account status"), `stripe_customer_id` (nullable, unique — one Stripe Customer per user, created lazily on first checkout), `stripe_subscription_id` (nullable), `stripe_subscription_status` (nullable — mirrors Stripe's own `subscription.status` values verbatim, kept in sync only by the webhook handler), `stripe_cancel_at_period_end` (default `false` — tracked separately from `stripe_subscription_status` because Stripe's own status stays `'active'` through the paid period even after cancellation is requested — see `CLAUDE.md` → "Decided: billing"), `password_changed_at` (nullable — `NULL` until a first reset; `getCurrentUserId()` rejects any session JWT whose `iat` predates this timestamp, which is what makes a password reset invalidate sessions already active elsewhere despite sessions being stateless JWTs — see `CLAUDE.md` → "Decided: rate limiting & password reset"). Written to by `app/api/auth/signup/route.ts`, read by `app/api/auth/login/route.ts`, by the worker (to find the address for the "ready" email), and by `app/(app)/layout.tsx` (whether to show the verify-email banner, and whether to render the Admin nav link) — email+password auth is built, see `CLAUDE.md` → "Decided: auth mechanism" and "Decided: email verification". Nothing currently reads `phone` — captured for future use, not acted on. `token_balance` is genuinely money-backed via real (test-mode) Stripe purchases **and** now genuinely deducted on upload/extension — see `CLAUDE.md` → "Decided: token enforcement & expiry extension".
- `sessions` — a real lifecycle, not just a log: `id` (UUID PK), `user_id` (FK → `users`, `ON DELETE CASCADE`, `NOT NULL`), `original_filename`, `status` (`queued` / `processing` / `complete` / `downloaded` / `expired` / `failed`, default `'queued'`), `error_message`, `expires_at` (nullable, set to `NOW() + INTERVAL '1 hour'` when a job completes, bumped by another hour on a paid extension), `extended` (`BOOLEAN NOT NULL DEFAULT FALSE` — whether the one allowed paid extension has been used), `created_at`/`updated_at`. Indexed on `user_id`. Still no `video_key`/`image_key` — the actual file lives transiently on disk (`SHARED_TEMP_DIR`, see `architecture.md`), never referenced by a DB column, so there's no persistent pointer to clean up or worry about leaking.
- `token_grants` — `id` (UUID PK), `user_id` (FK → `users`, `ON DELETE CASCADE`, `NOT NULL`), `tokens` (positive for additions, **negative for usage charges**), `amount_cents` (nullable — `NULL` for a comp/admin grant, a usage charge, or a refund; only set for a real purchase — this is what keeps the admin page's revenue total honest regardless of the other row types mixed into this same table), `source` (`subscription`/`pay_as_you_go`/`admin_grant`/`usage_upload`/`usage_extend`/`refund`), `note` (nullable), `stripe_reference` (nullable — the PaymentIntent or Invoice id that produced this grant, for support/debugging; `NULL` for admin comps/usage rows, which have nothing to point to), `session_id` (nullable FK → `sessions`, `ON DELETE SET NULL` — links a usage charge/refund to the session that caused it; the worker's refund-on-failure logic looks up "how much was this session charged" via this column rather than a separate `sessions.tokens_charged` field), `created_at`. Indexed on `user_id` and `session_id`. Every change to `users.token_balance` should have a corresponding row here — the balance is a derived running total, the ledger is the source of truth.
- `stripe_webhook_events` — `id` (Stripe's own `event.id`, e.g. `evt_...`, TEXT PK — the natural idempotency key), `type`, `processed_at`. No FK to anything — this is a pure claim table (`INSERT ... ON CONFLICT (id) DO NOTHING RETURNING id`) that makes a redelivered/resent webhook event a safe no-op instead of a double-grant. See `CLAUDE.md` → "Decided: billing".
- `rate_limit_attempts` — `id` (UUID PK), `key` (an email or client IP, depending on `action`), `action` (`login`/`signup`/`forgot-password`), `created_at`. Indexed on `(key, action, created_at)` for the windowed `COUNT(*)` `lib/rateLimit.ts` runs. No FK — a plain attempt log, pruned by the worker's scheduled cleanup job (rows older than 24h) rather than left to grow forever. See `CLAUDE.md` → "Decided: rate limiting & password reset".

## Notable patterns

- `users.email` has a `UNIQUE` constraint that's actually relied on — the signup route inserts directly and catches Postgres error `23505` (unique_violation) rather than doing a pre-check `SELECT` first, which would leave a race window between the check and the insert.
- **`sessions.status` transitions are enforced by `UPDATE ... WHERE status = 'x'` clauses, not application-level locking.** Two places rely on this: the worker's job handler only ever moves a session forward (`queued`→`processing`→`complete`), and the download route's claim step (`UPDATE sessions SET status = 'downloaded' ... WHERE status = 'complete' RETURNING id`) is what makes concurrent double-download attempts safe — if two requests race, only one `UPDATE` actually matches a row.
- `sessions.user_id` is now genuinely used everywhere: the upload route sets it, the dashboard/sessions pages filter by it (`getCurrentUserId()`), the download route checks it before serving anything.
- **Previously had `screenshots` and `transcript_segments` tables** (one row per detected slide, one per transcript segment) — removed 2026-08-12 when the storage model changed from "keep the output, let users re-download" to "one-time download, nothing kept." See `docs/changelogs/2026-08-12.md`.
- `expires_at`, the expanded `status` vocabulary, and (same day) `email_verified_at` were all added via real `ALTER TABLE` statements (2026-08-14) rather than from-scratch rewrites — real user accounts existed in the table by then, unlike earlier schema changes.
- **No verification-token table.** Verification links are self-contained JWTs (signed with `SESSION_SECRET`, same as sessions), not a stored/lookup-able token — see `CLAUDE.md` → "Decided: email verification" for why (and the purpose-scoping that keeps them from being confused with session tokens despite sharing a secret). Password-reset links (2026-08-14) follow the exact same pattern with their own `purpose` value.
- **Token debits use the same "atomic conditional UPDATE, not read-then-write" idiom as `sessions.status`** — `lib/tokens.ts`'s `chargeTokens()` does `UPDATE users SET token_balance = token_balance - $cost WHERE ... AND token_balance - $cost >= -100 RETURNING token_balance` in one statement, so Postgres's row-level locking (not application code) is what prevents two concurrent charges from jointly pushing a balance past the -100 floor. See `CLAUDE.md` → "Decided: token enforcement & expiry extension".
