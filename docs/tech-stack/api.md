# API

Route handlers under `app/api/`. Pages themselves (`app/(app)/dashboard/page.tsx`, `app/(app)/sessions/page.tsx`) still query Postgres directly via `lib/db.ts` in server components — the API layer exists for actions a client component needs to trigger (auth, upload, download), not for reads a server component can just do itself.

| Route | Method | Purpose |
|---|---|---|
| `/api/auth/signup` | POST | Create a user (email/password validated, hashed via `bcryptjs`), issue a session cookie |
| `/api/auth/login` | POST | Verify credentials, issue a session cookie. Generic "Invalid email or password" on any failure — no user-enumeration |
| `/api/auth/logout` | POST | Clear the session cookie |
| `/api/auth/verify` | GET | `?token=<jwt>`. **No auth check** — the token itself proves email ownership, someone might click it from a different browser. Sets `email_verified_at`, redirects to `/dashboard?verified=success` or `?verified=error` |
| `/api/auth/resend-verification` | POST | Auth-gated. Issues a fresh verification token, refuses if already verified |
| `/api/auth/forgot-password` | POST | Body `{ email }`. Rate-limited (5/15min by email). **Always returns `{ok:true}`** regardless of whether the email exists — same enumeration-avoidance principle as login's generic error. Only sends if a matching user is found |
| `/api/auth/reset-password` | POST | Body `{ token, newPassword }`. **No auth check** — same "the token is the proof" pattern as `/api/auth/verify`. Verifies a `purpose: "password-reset"` JWT (30min expiry), updates `password_hash`, and clears any existing login rate-limit lockout for that email |
| `/api/sessions` | POST | Upload a video. Auth-gated. Raw streamed body, not multipart form-data (filename via an `X-Filename` header) — validates it's a video file under 6GB, creates a `sessions` row (`status = 'queued'`), streams the body straight to local scratch disk, then streams that file on to B2 (`putObjectStream()`). Never buffered whole in memory — see `CLAUDE.md` → "Decided: streaming upload". **Probes duration via `ffprobe` and charges tokens** (`1/minute, rounded up, min 1`) before enqueueing — allowed to push `token_balance` down to -100, rejected (400, B2 object never created or deleted, no charge) beyond that. If enqueueing itself then fails, the charge is refunded in the same request |
| `/api/sessions/[id]/extend` | POST | Auth-gated (must own the session). One transaction: an atomic conditional `UPDATE` bumps `expires_at` by 1 hour and sets `extended = TRUE` (0 rows matched → 400, covers already-extended/expired/wrong-status/not-yours in one shot), then charges 50 tokens the same way the upload route does. A failed charge rolls back the `expires_at` bump too, since nothing committed yet |
| `/api/sessions/[id]/download` | GET | Auth-gated (must own the session). Atomically claims the session (`UPDATE ... WHERE status = 'complete' RETURNING id`) before touching the file — the real concurrency guard against a double-download race. **Streams the zip from B2** (`HeadObjectCommand` for size, `GetObjectCommand`/`Readable.toWeb()` for the body, not buffered into memory) — deletes the B2 object immediately after opening the stream (confirmed for real that this doesn't truncate an in-flight download, not just assumed from POSIX), marks `downloaded`. Lazily flips overdue `complete` rows to `expired` and refuses instead of serving — now a backstop for the worker's real 15-minute scheduled sweep, not the only enforcement |
| `/api/admin/grant-tokens` | POST | **Admin-gated**, not just auth-gated — checks `users.is_admin` independently of whether the caller could see the nav link or the page. Body `{ userId, tokens }`, `tokens` must be a positive integer. Inserts a `token_grants` row (`source = 'admin_grant'`, `amount_cents = NULL`) and increments `users.token_balance` in one transaction |
| `/api/admin/set-account-status` | POST | **Admin-gated**, same independent `is_admin` check. Body `{ userId, status }`, `status` must be one of `active`/`paused`/`revoked`. Refuses with 400 if `userId` equals the caller's own id — an admin can't lock themselves out. Takes effect immediately, not just at next login — see `CLAUDE.md` → "Decided: account status" |
| `/api/stripe/create-payment-intent` | POST | Auth-gated. Body `{ packId }`, validated against `lib/tokenPacks.ts` server-side — the client never sends a dollar amount. Gets/creates the caller's Stripe Customer, creates a PaymentIntent for the pack's amount with `metadata.source = "token_pack"` (load-bearing — see the webhook row below). Returns `{ clientSecret }` for Stripe Elements |
| `/api/stripe/create-subscription` | POST | Auth-gated. 400 if already `active`/`trialing`/`past_due`. Creates a Stripe Subscription against `STRIPE_SUBSCRIPTION_PRICE_ID` with `payment_behavior: "default_incomplete"`, `expand: ["latest_invoice.confirmation_secret"]` (the nested expand is required — a bare `expand: ["latest_invoice"]` does not populate `confirmation_secret`, despite the Stripe SDK's own TypeScript types not flagging it as needing a separate expand). Returns `{ clientSecret }` |
| `/api/stripe/cancel-subscription` | POST | Auth-gated. `stripe.subscriptions.update(id, { cancel_at_period_end: true })` — graceful, keeps access through the paid period. Doesn't update the DB itself; the `customer.subscription.updated` webhook is the single source of truth for `stripe_subscription_status`/`stripe_cancel_at_period_end` |
| `/api/webhooks/stripe` | POST | **No auth check** — Stripe isn't a logged-in user. Verifies `stripe-signature` against the **raw** request body (`await request.text()`) before touching the database; anything that fails verification is rejected with 400. Idempotency (`stripe_webhook_events`, keyed on Stripe's `event.id`) is claimed inside the same transaction as the grant it guards. Handles `payment_intent.succeeded` (pack purchases — gated on `metadata.source === "token_pack"` to avoid double-granting alongside a subscription's own first-invoice PaymentIntent), `invoice.paid` (subscription grants, first payment and every renewal), `customer.subscription.updated`/`.deleted` |

No API versioning. All responses are JSON via `NextResponse.json()` except `/api/auth/verify` (redirect) and the download route (raw zip bytes, `Content-Type: application/zip`).

## Conventions

- Dynamic route params are `Promise`-typed and awaited (Next.js 16 convention): `{ params }: { params: Promise<{ id: string }> }`.
- No request validation library (no Zod) — bodies are read directly and checked by hand (email regex, password length, file type/size).
- Auth check is `getCurrentUserId()` (`lib/auth.ts`) at the top of each protected handler, not middleware — see [`architecture.md`](./architecture.md) → "Middleware". `/api/auth/verify` is the one deliberate exception — see its row above.
- **Route folder names starting with `_` don't route at all** — Next.js treats them as private folders, excluded from the router entirely. Learned the hard way building a temporary test-only route as `app/api/_test-only/...` (silent 404) before renaming it without the underscore.
- **Rate limiting is per-route, not middleware-wide** (`lib/rateLimit.ts`, backed by `rate_limit_attempts`) — applied to `login`/`signup`/`forgot-password` only, each with its own key (email for login/forgot-password, client IP for signup) and threshold. See `CLAUDE.md` → "Decided: rate limiting & password reset".
