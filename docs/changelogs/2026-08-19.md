# Changes — August 19, 2026

## Sessions page: real user timezone, token cost, and processing time shown per session

Three related fixes/additions caught while checking the Sessions page during tonight's RunPod testing.

**Timestamps were wrong for anyone not in the Railway container's own timezone.** `app/(app)/sessions/page.tsx` is a server component calling `new Date(...).toLocaleString()` directly — that formats using whatever timezone/locale *the server* runs in (Railway's container, effectively UTC), not the actual user's. Fixed by moving all timestamp formatting into a new client component, `components/SessionMeta.tsx`, so `toLocaleString()`/`toLocaleTimeString()` run in the browser and pick up the real local timezone automatically — no manual timezone detection needed, the browser already knows. Uses `useSyncExternalStore` (not `useState`+`useEffect`) to give the server and client different snapshots — `false` during SSR, `true` once hydrated — avoiding the `react-hooks/set-state-in-effect` lint rule's "cascading renders" warning that the more obvious `useEffect(() => setMounted(true))` pattern trips.

**Added token cost per session.** `sessions/page.tsx`'s query now `LEFT JOIN`s `token_grants` on `session_id` where `source = 'usage_upload'` (`ABS(tg.tokens)`, since usage charges are stored negative — see "Decided: token enforcement & expiry extension") — at most one such row can exist per session, so a plain join can't duplicate rows. Shows as "N tokens" in the same meta line as the timestamp.

**Added actual processing time per session.** Nothing in the existing schema could answer "how long did this take" — `updated_at` gets overwritten by every later transition (`complete` → `downloaded` → `expired`), so it can't be trusted to still hold the "just finished" moment by the time someone loads the page. Added two new nullable columns, `sessions.processing_started_at`/`processed_at` (`lib/migrate.ts`), set by `worker/index.ts` at the two exact moments that matter — right before `runGpuPipeline()` is called and right after it returns — which also means this duration captures the *real* user-facing latency (RunPod queue delay + cold start + actual execution), not just execution time alone. Shown as "processed in Nm Ns" once both timestamps exist. `setStatus()`, now with only one caller, was inlined and removed.

**Also added**: `components/Footer.tsx` — a "Designed by Light Patterns" attribution bar (same pattern as the other Light Patterns apps, e.g. `mix_bar`'s `Footer.jsx`, but just the bottom-bar piece, not a full multi-column footer — a SaaS app's public page has no hours/location section to show), wired into `app/(marketing)/layout.tsx` below `{children}`.

Migration run locally (`npm run migrate`) to confirm the new columns apply cleanly. `npx tsc --noEmit` and `npm run lint` both pass. **Committed locally only, not pushed**, per instruction — production's `sessions` table doesn't have these columns yet, so don't deploy this without also running the migration there.

## Fixed: false "Upload failed" banner on a mid-upload server redeploy

Caught live: uploading a real ~1.5GB `.mov` right as Railway redeployed the worker service (adding the RunPod env vars above triggered it) showed a client-side "Upload failed" banner — but the session itself actually went `QUEUED` → `PROCESSING` and correctly charged tokens, proving the upload had genuinely succeeded server-side despite the error shown to the user.

**Cause**: `components/UploadProvider.tsx`'s `xhr` fires a network-level `"error"` event (distinct from a clean non-2xx HTTP response) when the underlying connection is severed before a response arrives — exactly what happens when the server process handling the request gets killed mid-response by a redeploy. `app/api/sessions/route.ts` had, by that point, already finished the whole flow (session row created, tokens charged, job enqueued) — the *confirmation* just never made it back to the browser. The client had no way to distinguish that from a real failure.

**Fix, not a blanket "assume success" hack**: `recentNonFailedSessionExists()` (new, in `UploadProvider.tsx`) polls the new `GET /api/sessions/latest` (new route, returns the current user's single most recent session's `id`/`status`/`createdAt`) up to 4 times over ~8 seconds after an `"error"` event, specifically looking for a session created at/after the upload's own start time that isn't `'failed'`. Only if the grace period finds no such session does it fall back to the original "Upload failed" message — so a truly failed upload (bad network throughout, server never even got the request) still shows the error, just after a short wait instead of instantly.

**Deliberately scoped to the network-level `"error"` event only**, not the existing non-2xx `"load"` branch — a real HTTP error response means the server already made a definitive decision and already called `markFailed()` to match it in the DB, so there's nothing ambiguous to wait out there; showing that error immediately is still correct.

**Not yet verified against a real repeat of the failure mode** (would need another mid-upload redeploy to reproduce exactly) — reasoned through and typechecked/linted clean, but the actual grace-check timing under a real network hiccup is the next thing to confirm. Committed locally only, not pushed, per instruction.

## Zlib fix confirmed — transcode/scene-detection/zip/B2 all real now, whisper-cli still broken

**Real, unexpected discovery mid-process**: a successful build doesn't automatically roll out to already-running RunPod workers — an idle worker from an earlier test kept serving the *old* image (confirmed by the same `workerId` handling two different test jobs, and cold start dropping from ~75s to ~7s on the reused worker). The zlib-fix commit's build only actually started ~50 minutes after being pushed and took the usual 20-40 min CUDA compile; once it finished it did auto-promote to a new Release, and a fresh worker picked it up correctly.

**Retested the original synthetic 2-scene video against the new build — real success**: `unzip -t` passed clean, `video.mp4` is a genuine h264/aac file at the exact correct 8.01s duration, both screenshots match the 2 synthetic scene changes. **Confirms transcode (NVENC), scene detection, zip packaging, and B2 upload/download all genuinely work now** — verified by downloading the real produced zip from B2 and inspecting it directly, not by trusting the job's "complete" status alone.

**Transcription itself was still unverified** — that first test's audio was a pure sine tone, so whisper correctly found nothing to transcribe and used the honest fallback message, which doesn't prove the CUDA whisper path actually works. Generated a second synthetic test video with **real narrated speech** (macOS `say` + `ffmpeg`, same technique already used to verify the CPU whisper.cpp path) and ran it through the same RunPod endpoint. **Still hit the fallback message** — a real bug this time, not an expected no-op. Checked RunPod's Logs tab directly (not derivable from the job status API, which doesn't surface a succeeded job's internal stdout) and found the actual cause: `whisper-cli: error while loading shared libraries: libgomp.so.1: cannot open shared object file`.

**Cause**: GCC's OpenMP runtime (`libgomp1`) is a real runtime dependency of whisper.cpp even in a CUDA build (`ggml` uses OpenMP for its CPU-side ops) — present in the Dockerfile's *build* stage via `build-essential`, but never installed in the slim `nvidia/cuda:12.4.1-runtime-ubuntu22.04` final stage.

**Fix**: added `libgomp1` to the final stage's `apt-get install` line in `worker/runpod-handler/Dockerfile`.

**Not yet re-verified** — same pattern as every fix tonight: the next build + a re-run of the speech test is the actual test, not this diagnosis.

## Fixed: RunPod build failure — wrong Docker build context assumed

Deployed the RunPod Serverless endpoint (`screenScribe`, Queue-based, 16GB GPU tier — RTX 2000/4000 Ada, A4000, A4500 all enabled, `$0.58/hr` — B2 credentials stored as RunPod Secrets rather than plaintext env vars) and its first build failed immediately: `failed to calculate checksum of ref ...: "/handler.py": not found`.

**Cause**: `worker/runpod-handler/Dockerfile`'s `COPY handler.py .` / `COPY requirements.txt .` assumed the build context was the Dockerfile's own directory — true for the existing `worker/Dockerfile` under Railway, which lets you set `worker/` as a service's own root directory (so its context really is `worker/`, and `COPY . .` works). RunPod's GitHub-deploy build has no equivalent per-service root-directory setting exposed in the UI actually used here — it builds with the **repo root** as context regardless of where the Dockerfile itself lives, so `COPY handler.py .` was looking for `/handler.py` at the repo root, which doesn't exist.

**Fix**: both `COPY` lines now spell out the full repo-root-relative path (`COPY worker/runpod-handler/handler.py .`, same for `requirements.txt`) instead of assuming the Dockerfile's own directory is the context.

**Not yet verified** — this fixes the specific failure seen in the build log, but the image hasn't finished a real build yet; the next RunPod build attempt is the actual test.

## Fixed: second build failure — root `.dockerignore` excluding `worker/`

The path fix above got `requirements.txt` copying, but the very next `COPY worker/runpod-handler/handler.py .` still failed as "not found" on the retry. Root cause: the repo's shared root `.dockerignore` has a bare `worker` line — correct for the *other* two Dockerfiles (keeps the web app's build context from pulling in the worker's `node_modules`), but wrong for this one, since RunPod's build context is the repo root and this Dockerfile specifically needs files under `worker/runpod-handler/`. That line excludes the entire `worker/` tree from every build using repo-root context, this one included.

**`worker/runpod-handler/Dockerfile.dockerignore`** (new) — a Dockerfile-scoped ignore file (same directory as the Dockerfile itself, BuildKit's documented override mechanism since Docker Engine 23.0) that replaces the root `.dockerignore` for this build specifically, without touching what the other two Dockerfiles rely on. Excludes `node_modules`, `.git`, `.next`, `.env*`, `docs`, `*.log`, `worker/models` (the 500MB gitignored whisper model, irrelevant to this GPU build since it fetches its own model via `curl` in its own build stage) — deliberately omits the bare `worker` exclusion that caused the failure.

**Also caught while debugging this**: `worker/runpod-handler/__pycache__/handler.cpython-39.pyc` had been accidentally committed (a byproduct of a local `python3 -m py_compile` syntax check earlier tonight) — the repo had no `__pycache__`/`*.pyc` rule in `.gitignore` since this is otherwise an all-TS/JS codebase. Added both patterns to `.gitignore` and untracked the file with `git rm --cached`.

**Still not verified against a real successful build** — the next RunPod build attempt is the real test of both fixes together.

## RunPod Serverless handler — first step toward replacing the CPU-only Railway worker

The Railway worker's two real problems: uploads take too long (a separate, still-open problem — see the note below), and processing takes too long because the worker's whisper.cpp runs CPU-only, no Metal/CUDA, on the Linux Railway container. Compared GPU cloud options (serverless pay-per-second platforms vs. traditional GPU VMs, price/video, price/month, speed estimates) and picked **RunPod Serverless** — purpose-built for async queue-shaped jobs, true per-second billing with no monthly minimum, custom Docker images, and a public Whisper worker template to start from. Chosen over Modal (same fit, but its $30/mo recurring credit read as a monthly cost rather than the free credit it actually is) and over traditional GPU VMs (would mean paying for 24/7 idle time again, the same problem as today's always-on Railway worker, unless started/stopped per job).

**`worker/runpod-handler/`** (new, separate from `worker/index.ts`) — a thin Python package containing only the GPU-bound half of the pipeline: download the raw upload from B2, transcode to mp4 (NVENC, not libx264 — the CPU worker's libx264 choice was specifically about matching encoder behavior between the Mac dev machine and the equally-CPU-only Railway worker, which doesn't apply here), detect scene changes (unchanged — still a CPU-bound ffmpeg decode/diff, threshold 0.3, same `eq(n,0)` first-frame fix as the Node version), extract 16kHz mono audio, transcribe via a CUDA-built `whisper-cli` (same `medium`/`q5_0` model as the CPU worker — not re-evaluating that choice, just carrying it over), zip in the same `video.mp4` / `transcript.txt` / `screenshots/screenshot-NNNN.png` layout the download route already expects, and upload the zip back to B2. Mirrors `worker/lib/ffmpeg.ts`/`whisper.ts`/`b2.ts` closely enough to keep the two implementations in sync by inspection.

**Deliberately does not touch Postgres, token charge/refund, email, or `sessions.status`** — RunPod's serverless model is HTTP-triggered, not a queue-poller, so `worker/index.ts` keeps doing all of that orchestration exactly as today; it will need a dispatcher change (call RunPod's API instead of running ffmpeg/whisper locally) to actually use this — **not built yet, scoped as a separate next step.**

- **`worker/runpod-handler/Dockerfile`** — NVIDIA CUDA base images (`devel` for the build stage, `runtime` for the final image), not `node:22-slim` — this container only needs Python (RunPod's SDK is Python-first) and compiled binaries. Compiles ffmpeg from source against `nv-codec-headers` with `--enable-nvenc --enable-cuvid --enable-libnpp` (Ubuntu's apt `ffmpeg` package isn't built with NVENC support), and whisper.cpp with `-DGGML_CUDA=ON` (auto-offloads to GPU, no extra runtime flag needed) — same "compile from source, only copy the resulting binary" pattern the existing `worker/Dockerfile` already uses for whisper.cpp on the CPU path.
- **`worker/runpod-handler/handler.py`** — `runpod.serverless.start({"handler": handler})`, receives `{"sessionId": "..."}`, does the pipeline above, returns `{"status": "complete", "sessionId": ...}` or raises. B2 credentials come from RunPod endpoint environment variables (same `B2_ENDPOINT`/`B2_BUCKET_NAME`/`B2_APPLICATION_KEY_ID`/`B2_APPLICATION_KEY` the Node worker already uses), not baked into the image.
- **Not yet verified against real hardware** — no NVIDIA GPU on this dev machine to test the CUDA/NVENC path locally, same position the CPU whisper.cpp Dockerfile was in before its first real Railway build. The first real RunPod build + invocation is the actual test, not this code.

## Dispatcher change — worker/index.ts now calls RunPod instead of running ffmpeg/whisper locally

**`worker/lib/runpod.ts`** (new) — `runGpuPipeline(sessionId)` POSTs `{"input": {"sessionId": ...}}` to RunPod's async `/run` endpoint, then polls `/status/{jobId}` every 5s until a terminal state. Async `/run` + poll, not the synchronous `/runsync` — `/runsync` enforces its own request timeout, unsuited to a job that can run several minutes of GPU time plus queue wait. Needs `RUNPOD_API_KEY`/`RUNPOD_ENDPOINT_ID` in `worker/.env.local` — not set yet, since there's no deployed RunPod endpoint to point at until the account/image from tonight's earlier work is actually deployed.

**`worker/index.ts`'s `processSession()`** now calls `runGpuPipeline(sessionId)` in place of the old inline `transcodeToMp4`/`extractSceneFrames`/`extractAudioWav`/`transcribeAudio`/zip/upload sequence — that entire pipeline now runs inside the RunPod handler (see above), which already talks to B2 directly. Removed the now-dead `downloadInputFile`/`zipResults` helpers and their now-unused imports (`archiver`, `node:fs`/`node:fs/promises` file helpers, `lib/ffmpeg`, `lib/whisper`, `lib/tempStorage`).

- **A real, known regression, not an oversight**: the old per-stage `sessions.status` values (`transcoding`/`detecting_scenes`/`transcribing`/`packaging`) that drove the Sessions page's animated stepper (`SessionStageProgress.tsx`) are gone — the status now just sits at `processing` for the whole RunPod job, since there's no visibility into which internal step an opaque RunPod job is on from here. Recovering that granularity would mean either RunPod's progress-update mechanism or a webhook callback from the handler — deliberately not built now, flagged as a follow-up if the coarser stepper turns out to matter.
- **`worker/lib/ffmpeg.ts`, `worker/lib/whisper.ts`, `worker/lib/tempStorage.ts` are now unused** (confirmed via `grep` — nothing left imports them) but **deliberately not deleted yet** — they're still what the existing CPU `worker/Dockerfile`/Railway deploy depends on, and cutting them now would remove the ability to fall back to the CPU path during the transition, before the RunPod endpoint has actually been proven out against a real job. Worth revisiting once RunPod is confirmed working end-to-end and the Railway worker is actually decommissioned, not before.
- `npx tsc --noEmit` passes clean against the new imports/removed code.
- **Still not done**: RunPod endpoint isn't deployed yet (this session picked "Serverless" as the product type in RunPod's UI but didn't finish deploying), so `runGpuPipeline` has never actually been invoked against a real job — same "first real invocation is the actual test" caveat as the handler itself.
