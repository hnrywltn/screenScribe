# Changes — August 20, 2026

## Added: receipt email after a token pack purchase or subscription payment

`lib/email.ts` gains `sendReceiptEmail(to, { tokens, amountCents, kind })` — same raw-fetch-to-Resend pattern as the other account emails, subject/body varying slightly for a one-time pack ("Your StudyBeacon purchase receipt") vs. a subscription payment ("Your StudyBeacon subscription receipt", since `invoice.paid` also fires on renewals, not just the first payment).

`app/api/webhooks/stripe/route.ts`'s `payment_intent.succeeded` and `invoice.paid` handlers now capture the buyer's email (added to the existing `UPDATE users ... RETURNING`/`SELECT` queries — no new query needed) and the send happens **after `COMMIT`**, not inside the transaction — a failed email should never roll back a real token grant. The send itself is wrapped in its own `try`/`catch` (same pattern already used at the signup verification-email call site) so a Resend failure doesn't turn into a webhook 500 that makes Stripe retry an event whose grant already committed.

Confirmed via `npx tsc --noEmit` and `npm run lint`, both clean. Not yet verified against a real Stripe test-mode purchase — worth a real end-to-end check (buy a pack, subscribe) the next time billing is being tested live.

## Added: SMS notifications (Twilio) — upload started / download ready

Real Twilio account set up (Individual/sole-proprietor compliance profile, a purchased local number `+15106941850`, A2P 10DLC Brand + Campaign registered — Campaign submitted, status **In Review** as of tonight, not yet approved). `lib/sms.ts` / `worker/lib/sms.ts` (new, deliberately duplicated across packages — same convention as `email.ts`) send via raw `fetch` to Twilio's REST API rather than the `twilio` SDK, matching the "no SDK dependency needed for one endpoint" reasoning already used for Resend. Both no-op with a log line if `TWILIO_ACCOUNT_SID`/`TWILIO_AUTH_TOKEN`/`TWILIO_PHONE_NUMBER` aren't set, same fallback shape as the email functions.

Two send points, wired to fire only when both a phone number and `users.sms_opt_in` are set:
- `app/api/sessions/route.ts` — right after a successful upload finishes charging and enqueueing the job (an extra `SELECT phone, sms_opt_in` after the existing charge/enqueue logic, wrapped in its own try/catch so a failed text can't fail an otherwise-successful upload).
- `worker/index.ts`'s `processSession()` — alongside the existing `sendDownloadReadyEmail` call, once `status` flips to `complete` (the existing user lookup query was extended to also select `phone`/`sms_opt_in`, no new query needed).

Message copy deliberately has **no embedded link** (per instruction) — "log in to download" instead of a raw URL — which also kept the A2P Campaign registration simpler (no "Embedded links" content-type disclosure needed).

**New required infrastructure for A2P compliance, not previously built**: `app/(marketing)/privacy/page.tsx` and `.../terms/page.tsx` (real pages, not stubs — the privacy policy has an explicit SMS section covering message types, frequency, rates disclosure, and HELP/STOP), linked from `components/Footer.tsx` site-wide. `users.sms_opt_in BOOLEAN NOT NULL DEFAULT FALSE` (new migration) — TCPA requires affirmative opt-in, so this defaults false even for existing users who already had a phone number on file before this column existed. `SignupForm.tsx` gained an unchecked-by-default consent checkbox with the exact disclosure language + ToS/Privacy links Twilio's own campaign-registration guidance asked for; `app/api/auth/signup/route.ts` only stores `sms_opt_in = true` if a phone number was actually provided (checking the box with no number is a no-op, not an error).

**Custom domain went live tonight too**: `www.studybeacononline.com`, added and DNS-verified in Railway, pointing at the `screenScribe` web service. The `/privacy` and `/terms` URLs given to Twilio's campaign registration form point at this domain, not the Railway-generated one — confirmed live (200, correct content) after pushing.

Verified: `npx tsc --noEmit` and `npm run lint` clean in both packages. A real test text sent via `lib/sms.ts` to a personal number was accepted by Twilio's API (no error) but did not arrive — expected, since the A2P Campaign isn't approved yet and Verizon (the test recipient's carrier) is filtering unregistered traffic. Re-verify actual delivery once the Campaign clears review.

## Added: account settings page — SMS opt-in for existing users

Real gap found while setting up SMS: the opt-in checkbox only existed on the signup form, so any account created before tonight had no way to add a phone number or opt in at all. `app/(app)/account/page.tsx` (new, linked from `Sidebar.tsx`) + `components/AccountForm.tsx` (same phone field + consent checkbox/disclaimer as `SignupForm.tsx`) + `POST /api/account/update` (auth-gated, same validation and "consent only counts if a phone number was actually given" guard as the signup route).

Verified end-to-end with real requests against the dev account, not just typechecking: logged in, `GET /account` returned the form pre-filled with the current phone/opt-in state, `POST /api/account/update` with a real phone number + `smsOptIn: true` returned `200`, confirmed directly in Postgres that `phone`/`sms_opt_in` were actually written, and confirmed the page re-rendered with the saved values (`value="4155551234"`, `checked=""`) on reload. Reset the dev account back to a clean state (`phone = NULL`, `sms_opt_in = FALSE`) afterward.

## Production migration SQL — run before pushing tonight's SMS opt-in changes

Paste into Railway's Postgres SQL console (same approach as `docs/production-migrate.sql`, which has also been regenerated to include this column).
