# Changes — August 17, 2026

## Real object storage (Backblaze B2), replacing the local-disk file handoff

Set up a Backblaze B2 account and bucket (`screenScribe`, private, no encryption/Object Lock — Object Lock would fight the "delete on schedule" retention requirement), with a scoped application key (Read+Write, restricted to just this bucket — not the account master key). This replaces `SHARED_TEMP_DIR`, the local-dev-only shared-filesystem trick the web app and worker used to hand files to each other — flagged since 08-14 as something that "does not work once the worker is an actual separate Railway service." It now does.

- **`lib/b2.ts` / `worker/lib/b2.ts`** (new, deliberately duplicated — same convention as `email.ts`/`tempStorage.ts`, separate npm packages) wrap `@aws-sdk/client-s3` (`forcePathStyle: true` — B2 needs path-style addressing) plus, on the worker side, `@aws-sdk/lib-storage`'s `Upload` class for the finished-zip upload specifically, so a multi-hundred-MB zip never has to be buffered whole into memory just to supply a `Content-Length` upfront.
- **Key layout**: `uploads/<sessionId>/<original filename>`, `downloads/<sessionId>.zip` — both deterministic from `sessionId`, no new DB column needed, same reasoning the old `SHARED_TEMP_DIR` convention already used.
- **`LOCAL_SCRATCH_DIR`** (renamed from `SHARED_TEMP_DIR`, since the two services no longer need to agree on — or even share — a directory) is what's left of local disk: the web app briefly writes an upload there so `ffprobe` can read its duration before the bytes go to B2, and the worker downloads B2 objects there before handing local paths to `ffmpeg`. Both delete it immediately after their local use.
- **Upload route** (`app/api/sessions/route.ts`) now probes duration from the local copy *before* touching B2 at all — a corrupt file never costs a wasted upload — then `putObject()`s only on success, with `deleteObject()` cleanup on both remaining failure paths (insufficient balance, enqueue failure).
- **Worker** (`worker/index.ts`) lists the `uploads/<sessionId>/` prefix to find the file (mirrors the old `readdir()` lookup, since it doesn't know the filename ahead of time), downloads it to local scratch, processes exactly as before, uploads the finished zip via the streaming `Upload` class, deletes the `uploads/` object once packaging succeeds, and `rm`s local scratch regardless.
- **Download route** now does `HeadObjectCommand` for size and `GetObjectCommand` for the stream, and deletes the B2 object immediately after opening it — before piping to the client. This was a real open question going in: POSIX guarantees an open file descriptor after `unlink` (already verified for the old local-disk version), but there's no equivalent documented guarantee for a DELETE issued while a GET is still in flight against an S3-compatible API. **Verified for real rather than assumed** — see below.
- **Scheduled cleanup sweep** now issues `DeleteObjectCommand` against B2 instead of a local `rm()`.

**Verified end-to-end with a real synthetic video and real B2 API calls, not mocks**: generated a synthetic 10-second 2-scene video with `ffmpeg`, uploaded it through the real `/api/sessions` route, watched the worker log it move `processing` → `complete`, confirmed via a direct B2 listing that the `uploads/` object was gone and only the `downloads/` zip remained, downloaded it through the real download route, confirmed `Content-Length` matched exactly and `unzip -t` passed clean with a genuine h264/aac `video.mp4` at the correct 10-second duration and exactly 2 screenshots matching the 2 synthetic scene changes, confirmed a second download attempt correctly 410s, and confirmed via another direct B2 listing that the bucket was completely empty afterward. That last check is the one that mattered most: it confirms the delete-right-after-opening-the-stream pattern does not truncate an in-flight B2 download — not just carried over from the POSIX case by assumption.
