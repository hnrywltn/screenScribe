# Changes — August 17, 2026

## Real object storage (Backblaze B2), replacing the local-disk file handoff

Set up a Backblaze B2 account and bucket (`screenScribe`, private, no encryption/Object Lock — Object Lock would fight the "delete on schedule" retention requirement), with a scoped application key (Read+Write, restricted to just this bucket — not the account master key). This replaces `SHARED_TEMP_DIR`, the local-dev-only shared-filesystem trick the web app and worker used to hand files to each other — flagged since 08-14 as something that "does not work once the worker is an actual separate Railway service." It now does.

- **`lib/b2.ts` / `worker/lib/b2.ts`** (new, deliberately duplicated — same convention as `email.ts`/`tempStorage.ts`, separate npm packages) wrap `@aws-sdk/client-s3` (`forcePathStyle: true` — B2 needs path-style addressing) plus, on the worker side, `@aws-sdk/lib-storage`'s `Upload` class for the finished-zip upload specifically, so a multi-hundred-MB zip never has to be buffered whole into memory just to supply a `Content-Length` upfront.
- **Key layout**: `uploads/<sessionId>/<original filename>`, `downloads/<sessionId>.zip` — both deterministic from `sessionId`, no new DB column needed, same reasoning the old `SHARED_TEMP_DIR` convention already used.
- **`LOCAL_SCRATCH_DIR`** (renamed from `SHARED_TEMP_DIR`, since the two services no longer need to agree on — or even share — a directory) is what's left of local disk: the web app briefly writes an upload there so `ffprobe` can read its duration before the bytes go to B2, and the worker downloads B2 objects there before handing local paths to `ffmpeg`. Both delete it immediately after their local use.
- **Upload route** (`app/api/sessions/route.ts`) now probes duration from the local copy *before* touching B2 at all — a corrupt file never costs a wasted upload — then `putObject()`s only on success, with `deleteObject()` cleanup on both remaining failure paths (insufficient balance, enqueue failure).
- **Worker** (`worker/index.ts`) lists the `uploads/<sessionId>/` prefix to find the file (mirrors the old `readdir()` lookup, since it doesn't know the filename ahead of time), downloads it to local scratch, processes exactly as before, uploads the finished zip via the streaming `Upload` class, deletes the `uploads/` object once packaging succeeds, and `rm`s local scratch regardless.
- **Download route** now does `HeadObjectCommand` for size and `GetObjectCommand` for the stream, and deletes the B2 object immediately after opening it — before piping to the client. This was a real open question going in: POSIX guarantees an open file descriptor after `unlink` (already verified for the old local-disk version), but there's no equivalent documented guarantee for a DELETE issued while a GET is still in flight against an S3-compatible API. **Verified for real rather than assumed** — see below.
- **Scheduled cleanup sweep** now issues `DeleteObjectCommand` against B2 instead of a local `rm()`.

**Verified end-to-end with a real synthetic video and real B2 API calls, not mocks**: generated a synthetic 10-second 2-scene video with `ffmpeg`, uploaded it through the real `/api/sessions` route, watched the worker log it move `processing` → `complete`, confirmed via a direct B2 listing that the `uploads/` object was gone and only the `downloads/` zip remained, downloaded it through the real download route, confirmed `Content-Length` matched exactly and `unzip -t` passed clean with a genuine h264/aac `video.mp4` at the correct 10-second duration and exactly 2 screenshots matching the 2 synthetic scene changes, confirmed a second download attempt correctly 410s, and confirmed via another direct B2 listing that the bucket was completely empty afterward. That last check is the one that mattered most: it confirms the delete-right-after-opening-the-stream pattern does not truncate an in-flight B2 download — not just carried over from the POSIX case by assumption.

`CLAUDE.md` updated: new "Decided: object storage (B2)" section, the old "File handoff" gap under "Decided: pipeline orchestration" marked resolved, the "production file handoff" bullet removed from "Deliberately not built yet," and the `sessions` data-model note updated to describe the B2 key convention instead of `SHARED_TEMP_DIR`.

Token packs needed no equivalent live Product — `create-payment-intent` already builds `PaymentIntent`s directly from `lib/tokenPacks.ts`'s dollar amounts, no Stripe Price object involved.

- **`Dockerfile` (root) + `worker/Dockerfile`** (new), each `node:22-slim` with `apt-get install ffmpeg` — the web app needs `ffprobe` specifically (upload-time duration probing), the worker needs the full `ffmpeg` (transcode + scene detection). `.dockerignore` / `worker/.dockerignore` added alongside. Verified `npm run build` succeeds locally first, matching what the Docker `RUN npm run build` step would do, before trusting the Dockerfile against a real Railway build.
- **Real bug caught by the first Railway build, not local testing**: `lib/stripe.ts` constructed `new Stripe(process.env.STRIPE_SECRET_KEY!)` eagerly at module load — the Stripe SDK throws synchronously if `apiKey` is falsy, unlike `lib/db.ts`'s `Pool` (which tolerates an undefined `connectionString` at construction). `next build` evaluates route modules — and therefore their imports' top-level code — to collect config, even for `force-dynamic` routes, so a missing `STRIPE_SECRET_KEY` at *build* time (separate from runtime) crashed the entire build on `/api/stripe/cancel-subscription`. Fixed with a placeholder fallback (`|| "sk_build_placeholder"`) never actually used to make a request. Reproduced locally first (`env -u STRIPE_SECRET_KEY npm run build`) to confirm both the failure and the fix before pushing.
- **The actual Railway build queue was independently degraded** during part of this (Railway's own status page: "Deployments queued longer than usual," plus a simultaneous GitHub partial outage affecting pulls) — cost real time misdiagnosing a stuck build as a config problem before checking Railway's status page and confirming it was platform-side, not ours.
- **Production database was never migrated** — signup 500'd with `error: relation "rate_limit_attempts" does not exist` (Postgres `42P01`), confirmed directly from the web service's deploy logs rather than guessed at. `docs/production-migrate.sql` (new) is a plain, comment-free SQL export of `lib/migrate.ts`'s statements in the same order, for running through Railway's own SQL console since a direct psql connection wasn't set up — a one-time snapshot, not kept in sync automatically; regenerate it the same way if `lib/migrate.ts` changes before the next time prod needs a manual run.
- **Worker crash-loop diagnosed and fixed**: `ECONNREFUSED` on `localhost:5432` in the deploy logs — `DATABASE_URL` had simply never been set on the worker service (easy to miss when it was configured separately from the web service's 13 vars). Added `${{Postgres.DATABASE_URL}}` there, crash cleared.
- **Confirmed the whole pipeline actually works in production**: uploaded a real video through `screenscribe-production.up.railway.app`, watched it complete, downloaded a real zip with a genuine transcoded `video.mp4`, matching screenshots, and (at the time) the honest placeholder transcript.

## Real transcription — whisper.cpp wired up, replacing the placeholder

The last piece of the core pipeline that was still faked. `brew install whisper-cpp` locally (binary is `whisper-cli` in current versions, not the older `main`), model downloaded manually to `worker/models/ggml-medium-q5_0.bin` (gitignored, 514MB — not something to commit).

- **Quantization level pinned**: `q5_0`, chosen over `q4_0` for better accuracy while still clearing the already-established "faster than real-time" bar — confirmed on an M1 Pro with a synthetic narrated clip (macOS `say` + `ffmpeg`): 2.3s to transcribe an 11.4-second sample, correctly converting spoken "twenty three percent" to "23%".
- **`worker/lib/ffmpeg.ts`** gained `extractAudioWav()` — whisper.cpp needs a 16kHz mono WAV, not the mp4's own AAC stream.
- **`worker/lib/whisper.ts`** (new) — `transcribeAudio()` shells out to `whisper-cli`, reading stdout for the transcript itself (confirmed by testing the stdout/stderr split directly, not assumed) while stderr carries its backend-init diagnostic noise — same split convention `ffprobe`/`ffmpeg` already use elsewhere in this package.
- **`worker/index.ts`**: the old unconditional placeholder is now a try/catch around the real `extractAudioWav` → `transcribeAudio` call — a transcription failure degrades to an honest "transcription failed for this video" message rather than failing the whole job (the video + screenshots are still worth shipping), same principle as the old placeholder, just now scoped to the actual failure case.
- **`worker/Dockerfile`**: whisper.cpp isn't `apt`-installable, so it's compiled from source in a dedicated build stage (`build-essential`/`cmake`/`git`, statically linked so only one binary needs copying into the final image, not a pile of `.so` files) — both stages share the `node:22-slim` base so the compiled binary's glibc/libstdc++ actually match at runtime. The model file is fetched via `curl` in that same build stage and copied over, so the final image doesn't need `curl` at all. **Not verified against a real Railway build yet** — no Docker available on this machine to test-build locally first, unlike every other Dockerfile change tonight, so the next Railway deploy is the real first test of this specific piece.
- **Verified locally through the real pipeline, not the standalone CLI in isolation**: uploaded a real synthetic video (2 slides, real narrated speech) through the actual `/api/sessions` route, confirmed no transcription error in the worker log, downloaded the real zip, and confirmed the transcript inside was accurate and correctly timestamped.

`CLAUDE.md`'s "Decided: transcription" section updated to "built," the top project-status paragraph updated to stop calling out transcription as the missing piece, and the "Deliberately not built yet" bullet for it removed.

## In-progress uploads now show in Sessions, with a real Cancel button

Surfaced by a real question: does hitting back mid-upload actually stop it? It didn't — `UploadDropzone`'s `XMLHttpRequest` wasn't tied to the component's lifecycle at all, so navigating away left it silently finishing in the background, and its `load` handler still fired `router.push("/sessions")` afterward — a surprise forced navigation minutes later, not actually "lost" but arguably worse.

The real constraint driving the fix: the server has no idea an upload is happening until the *entire* multipart body has already arrived (`request.formData()` buffers the whole thing first) — so there's no DB row to poll during the transfer itself, only after. Showing progress + a cancel button had to be tracked client-side.

- **`components/UploadProvider.tsx`** (new) — a context mounted in `app/(app)/layout.tsx`, above `{children}`. That layout shell doesn't unmount when navigating within `(app)/` (only `children` does), so an upload started from `/upload` keeps running, stays cancelable, and stays visible from `/sessions` regardless of where the user navigates. Owns the `XMLHttpRequest` via a ref; `cancelUpload()` calls `xhr.abort()`.
- **`startUpload()` now navigates to `/sessions` immediately**, not on completion — replaces the old surprise-redirect-on-finish behavior. The user watches progress from the queue page itself, where the cancel button actually lives.
- **`components/UploadDropzone.tsx`** simplified to consume the context instead of owning its own XHR/progress state; **`components/ActiveUploadRow.tsx`** (new) renders the in-progress row (filename, progress bar, Cancel) above the real server-rendered rows on `/sessions` — a client component reading the same context, since the server-rendered `SessionsPage` has nothing to show yet.
- **Verified in a real browser, not just code review**: throttled upload bandwidth via a CDP session to make a tiny test file take several seconds, confirmed the row and Cancel button actually appear mid-upload, clicked Cancel, confirmed the row disappears cleanly — then confirmed directly in Postgres that **zero session rows were created** for that upload (cancelling before the full body arrives means the server-side handler, which creates the row after `request.formData()` resolves, never even runs). Separately verified a normal, non-cancelled upload still redirects immediately and the synthetic row gets correctly replaced by the real one once the server responds.

## Real animated per-stage progress, replacing the static "Processing…" label

`sessions.status` has always been plain TEXT with no `CHECK` constraint specifically so intermediate values could be added later without a migration — see CLAUDE.md "Decided: pipeline orchestration". Cashed that in: `worker/index.ts` now writes `transcoding` → `detecting_scenes` → `transcribing` → `packaging` at each real pipeline stage (a `setStatus()` helper, one line per stage, no schema change needed), instead of jumping straight from `processing` to `complete`.

- Installed `motion` (the current package name — confirmed `framer-motion` and `motion` are now the same release, `13.1.0`) for the animation.
- **`components/SessionStageProgress.tsx`** (new) — a 4-dot stepper with an animated connecting line that fills as each real stage completes, and a pulsing dot on whichever stage is currently active. Renders on the Sessions page under each session's filename, driven directly by `sessions.status` — not a simulated/fake progress bar.
- **Real bug caught by an actual browser screenshot, not just eyeballing the code**: the first version also printed all 4 stage labels under the dots (`justify-between` at a narrow width) — they visually collided into unreadable run-together text ("TRANSCODEDETECT SCENESTRANSCRIBEPACKAGE"). Fixed by dropping the labels entirely — the row's existing status badge (e.g. "PACKAGING…") already says the stage name, so they were redundant on top of being broken.
- **Verified with a real upload through the real pipeline**: rapid-polled a live upload and caught it mid-`transcribing`, then, since this tiny synthetic video moves through real stages in a couple seconds (too fast to reliably screenshot every stage via polling), set a completed test session's status directly in Postgres to get a clean, non-racy screenshot of the fixed stepper mid-stage — confirmed the dots/line render correctly with no more label collision, then restored the row's real status afterward.
