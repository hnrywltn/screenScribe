# Changes — August 12, 2026

## Discussed tutorial approach before building

Talked through the options for an onboarding tutorial: a tooltip/coachmark tour (Shepherd.js/Intro.js/driver.js-style, user-paced, no moving cursor), an auto-playing animated-cursor demo (matches "moving mouse walks through the UI" but needs a custom-built component, more fragile as the UI changes), or a recorded video walkthrough (simplest, but passive and goes stale). Decided on the tooltip/coachmark tour — good tradeoff of effort vs. payoff at this early stage, can revisit the animated-cursor idea once the real UI (upload flow, processing pipeline) exists and is more stable.

## Responsive layout pass

The app had no mobile handling — the sidebar was a fixed `w-56` flex child of a `flex` body, which would have squeezed page content into a sliver of the viewport on a phone. Reworked before adding the tutorial, since the tour needs to target real elements at both sizes:

- `app/layout.tsx` — body is now `flex-col` below `md`, `flex-row` at `md` and up; added `min-w-0` on `<main>` to stop flex's default `min-width: auto` from forcing horizontal overflow.
- `components/Sidebar.tsx` — split into two separate elements instead of one with responsive classes: a horizontal top bar (`md:hidden`, brand + inline nav links) and the original vertical sidebar (`hidden md:flex`). Both render the same nav links with matching `data-tour` attributes, which matters for the tutorial below.
- `app/page.tsx`, `app/sessions/page.tsx`, `app/upload/page.tsx` — responsive padding (`px-4 sm:px-8`, `py-6 sm:py-10`); home page grid goes `grid-cols-1` on mobile, `sm:grid-cols-2` up, so the two dashboard tiles stack instead of squeezing side by side.
- `app/sessions/page.tsx` — session list rows now `truncate` the name and `shrink-0` the status badge, so a long session name can't push the row into overflow on a narrow screen.

Verified with a Playwright script (headless Chromium, not part of the repo — one-off in scratch) at 1280×800 and 375×812: zero horizontal overflow at either width, and the sidebar/top-bar swap fires at the right breakpoint.

## Decided: business model, storage & retention, transcription, auth mechanism

Discussion, then a schema rewrite to match:

- **Business model**: ScreenScribe is a paid service (per-video or subscription, not yet decided which). This reframed the earlier storage discussion — minimal storage isn't just a privacy nicety, it's what makes the service costs scale sanely per user.
- **Storage & retention**: nothing persists past the download. A session's video, extracted screenshots, and transcript live only in an ephemeral temp directory during processing; once the zip is built and streamed to the browser, that directory is deleted. No re-download, ever. This retires the earlier "file storage backend TBD (R2 vs. B2 vs. local disk)" open item entirely — there's no backend to choose because there's no persistent file storage at all.
- **Transcription**: confirmed local-only — no cloud Whisper API, regardless of any provider's stated training/retention policy, since video content should never leave the machine. Leaning `whisper.cpp` (no Python dependency, Metal-accelerated on Apple Silicon), invoked as a local binary the same way ffmpeg will be.
- **Auth mechanism**: email + password, not OAuth or magic-link — keeps credentials in-house rather than depending on a third-party identity provider, and avoids adding an outbound-email dependency. Login/signup pages and session handling aren't built, just the mechanism decision.

### Schema rewrite

Pre-launch, local dev DB had zero real rows in any table, so rewrote `lib/migrate.ts` directly rather than layering `ALTER`/`DROP` statements on top of the old shape:

- **Removed** `screenshots` and `transcript_segments` entirely — there's no stored output left to describe.
- **Added** `users` (`email` unique, `password_hash`, `created_at`) for the future auth.
- **Rewrote** `sessions` from a rich processing record (`video_key`, multi-stage `status`, etc.) into a lean usage log: `user_id` (FK → `users`, `NOT NULL`), `original_filename`, `status` (`processing`/`complete`/`failed`), `error_message`, timestamps. No column points at stored content, because nothing is stored.
- Dropped the three old tables in the local `screenscribe` DB (confirmed empty first) and re-ran `npm run migrate` clean; re-ran a second time to confirm idempotency. `users` and `sessions` now exist with the expected FK/index.
- `app/sessions/page.tsx` updated to the new columns (`original_filename` instead of `name`), shows filename + formatted timestamp + status per row, with a note that it's not yet scoped to a logged-in user since login doesn't exist. Verified both `/` and `/sessions` still render correctly (200s, empty-state copy) against the new schema.

Updated `CLAUDE.md` and all of `docs/tech-stack/` to match — new "Decided:" sections for business model, storage & retention, transcription, and auth mechanism; explicitly flagged as **not built**: the pipeline itself, auth implementation (signup/login/sessions), and billing/payment integration (no `plans`/`credits` table invented).

## Decided: pipeline orchestration

Talked through synchronous request/response vs. background processing. Sync is ruled out — real videos take minutes to transcode/detect-scenes/transcribe, well past any HTTP/reverse-proxy timeout, and a held-open request has no way to show progress and loses the job entirely on a server restart. Also discussed whether a dedicated VM changes the picture (it does — a VM has no request-lifetime constraint at all, since a worker there isn't fulfilling anyone's HTTP request) and what VM options would look like (Railway worker service, a cheap generic VM like Hetzner/DO/Fly, AWS EC2 Mac instances for Metal-accelerated `whisper.cpp` in the cloud, or GPU rental if switching to a CUDA-based Whisper build).

**Decided: start with a second Railway service as the worker**, not a standalone VM — avoids introducing a new hosting vendor while still getting a persistent process with no request-timeout constraint. Paired with **`pg-boss`** (Postgres-backed job queue) rather than a Redis-backed queue (BullMQ etc.), reusing the Postgres already in the stack instead of adding a second infra dependency. Revisit a dedicated Metal-accelerated box only if transcription speed becomes a real problem under actual usage, not preemptively.

Also confirmed the three core deliverables haven't drifted from scope: screenshots, transcript, and format-converted video — all this conversation has settled is *how* they get produced, not *what* gets produced.

Recorded in `CLAUDE.md` (new "Decided: pipeline orchestration" section) and `docs/tech-stack/architecture.md`. Follow-up: worker repo layout resolved — it lives in **this repo**, a new `worker/` directory, deployed as a second Railway service from the same codebase rather than split out separately.

**Also resolved the file-handoff question** (asked for a call, made one): the worker sends the finished zip to the web app over Railway's private internal networking once a job completes, and the web app streams it to the browser — the worker never exposes its own public download endpoint. Reasoning: it keeps the worker (the service actually running ffmpeg/whisper.cpp on user-uploaded video) off the public internet entirely — smaller attack surface — and keeps the client talking to one origin instead of two (no CORS, one TLS cert). The alternative (worker serves a short-lived signed link directly) would've avoided one network hop, but that hop is a private in-datacenter transfer, not a real cost, so it lost to the security/simplicity win.

Pipeline orchestration is now fully decided end to end: `pg-boss` job queue, second Railway service as the worker, in this repo under `worker/`, handing the finished file back privately for the web app to stream out. Still nothing implemented — no `worker/` directory scaffolded, no `pg-boss` dependency added, no ffmpeg/whisper.cpp invocation code written. Next natural step is moving from architecture to actually building it, whenever that's wanted.

No DB changes.

## Scaffolded the worker package

Moved from architecture to a real, running piece of infrastructure — the pipeline logic itself is still a stub, but the worker now genuinely connects to Postgres and processes jobs.

- `worker/` — new **separate npm package** (own `package.json`, `tsconfig.json`, `.env.local`), not a subdirectory of the Next.js app's dependency tree. `npm install` run independently inside `worker/`, so its versions floated to whatever was current rather than being pinned to match root: `pg-boss` ^12.27.0, `pg` ^8.23.0, `dotenv` ^17.4.2, and dev deps `typescript` ^7.0.2 / `tsx` ^4.23.12 / `@types/node` ^26.2.0 — notably different majors from the root package's `typescript` ^5 / `@types/node` ^20.
- `worker/index.ts` — connects to `DATABASE_URL`, starts `pg-boss`, calls `boss.createQueue("process-session")` (required before `work()`/`send()` in this pg-boss version — confirmed by reading its type defs/README rather than assuming an older API), registers a handler, and shuts down cleanly on `SIGINT`/`SIGTERM`. The handler itself is a stub: logs the job's `sessionId` and does nothing else — no ffmpeg, no whisper.cpp, nothing enqueues real jobs yet since the web app has no upload endpoint.
- `worker/lib/db.ts` — same tiny `pg.Pool` singleton pattern as the root's `lib/db.ts`, duplicated rather than shared via a workspace setup (not worth the tooling complexity for four lines).
- **Caught and fixed a real problem before it caused confusion later**: the root `tsconfig.json`'s `**/*.ts` include glob was silently pulling `worker/*.ts` into the *root* TypeScript program, and it happened to resolve `pg-boss`'s types correctly (Node module resolution walks up from the importing file, so it found `worker/node_modules`) — meaning `npx tsc --noEmit` from the repo root was accidentally typechecking both packages as one, despite their diverging `@types/node` versions. It passed by luck rather than by design. Fixed by excluding `worker` in the root `tsconfig.json` and adding `worker/**` to `eslint.config.mjs`'s ignores — confirmed via `--listFiles`/`--debug` that neither root `tsc` nor root `eslint` touch `worker/` anymore, and that `worker/`'s own `tsc --noEmit` (run from inside `worker/`) still passes independently.
- Fixed `.gitignore`: `/node_modules` was anchored to the repo root only, so it wouldn't have caught `worker/node_modules`. Broadened to unanchored `node_modules`.
- **Verified end-to-end, not just "it starts"**: booted the worker (`npm run dev` from `worker/`), confirmed in `psql` that `pg-boss` provisioned its own `pgboss` schema (12 tables) in the local `screenscribe` database on first start, sent a real test job via a throwaway script (`boss.send("process-session", { sessionId: "test-session-id-123" })`), confirmed the running worker logged receiving and completing it, then sent `SIGTERM` and confirmed it shut down cleanly instead of hanging.

Updated `CLAUDE.md` (pipeline-orchestration section now describes the worker as scaffolded, not just decided; added a "Worker" commands block) and `docs/tech-stack/architecture.md`/`npm-packages.md` (new "Worker package" sections explaining the deliberate isolation from the root project).

No DB changes — `pg-boss`'s own schema doesn't count, that's its internal bookkeeping, not part of `lib/migrate.ts`.
