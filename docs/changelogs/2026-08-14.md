# Changes — August 14, 2026

## Building the upload flow: drag-and-drop, queue, notifications

Big feature — the actual upload → process → download path, not just infrastructure around it. Before writing code, settled two open design questions:

- **Notifications: email + in-app.** A 30–60 minute processing job means a user realistically walks away and comes back later, not watches a progress bar — email is the primary channel, the queue page shows live status for when they are in the app.
- **Download window: 1 hour.** Async job processing (already decided) put the "ephemeral, nothing kept around" storage promise in tension with reality — the finished file has to sit *somewhere* between "job done" and "user downloads it." Settled on a hard 1-hour expiry: matches a "process it, then go grab it" usage pattern, keeps the privacy promise meaningfully tight rather than "ephemeral" quietly becoming "kept around indefinitely." After expiry the file's gone — re-processing (and spending tokens again, once billing exists) is required.

**Two scope calls made explicit up front, not papered over:**
- **Local dev uses a shared temp directory** (`SHARED_TEMP_DIR`) between the web app and worker, since they're the same machine here. Production (separate Railway services, no shared filesystem) needs the real network-based handoff already decided but never built — flagged clearly as a gap, not pretended to be solved.
- **Resend** chosen for email (simple REST API, no SDK needed) — but there's no real API key configured, so sends will log instead of actually going out until one exists.
- **Uploads are unmetered for now** — token/billing enforcement isn't built, so this doesn't try to wire it in as a side effect of building the upload flow.

### Schema

`lib/migrate.ts` — first real `ALTER` on `sessions` rather than a from-scratch rewrite (real user accounts exist now, not just empty tables): `status` default changed to `queued`, added `expires_at TIMESTAMPTZ` for the download window. New lifecycle: `queued` → `processing` → `complete` → `downloaded`, or → `expired`/`failed`. Ran and re-ran to confirm idempotency.

### Job enqueueing from the web app

The web app previously had no way to create pg-boss jobs — only the worker did. Added `pg-boss` to the root `package.json` and `lib/queue.ts` (`sendProcessSessionJob(sessionId)`), a singleton client that lazily starts and idempotently ensures the `process-session` queue exists before sending, so it doesn't depend on the worker having started first.

### Upload UI

`components/UploadDropzone.tsx` — drag-and-drop or click-to-browse, client-side video-type/2GB size check before ever touching the network. Uses `XMLHttpRequest` instead of `fetch` specifically for its `upload.progress` event — a multi-hundred-MB video is exactly the case where a bare spinner isn't good enough feedback. Wired into `app/(app)/upload/page.tsx`, replacing the old "Coming soon" stub.

### Upload API route

`POST /api/sessions` — auth-gated, re-validates file type/size server-side (never trust the client check alone), inserts the `sessions` row first to get a real id, then writes the raw file to `SHARED_TEMP_DIR/uploads/<id>/` and enqueues the job. If anything fails after the row's created (disk write, enqueue), the session gets marked `failed` with a message rather than sitting stuck in `queued` forever with no explanation. Accepted the buffer-whole-file-in-memory tradeoff rather than building a streaming multipart parser — flagged as a real limitation for later, not hidden.

### Worker: the real job handler

This is the part that actually does the work now, not a stub that logs receipt.

- Added `archiver` to the worker package for zip packaging. Checked its actual README before writing code rather than assuming the API from memory — good thing: the installed v8 uses a class-based API (`new ZipArchive(...)`), not the older `archiver('zip', opts)` factory function pattern.
- `worker/lib/tempStorage.ts` (new, worker-side duplicate of the web app's own copy — separate packages, no shared import) — the filesystem convention both sides agree on: `uploads/<id>/`, `work/<id>/` (worker-only scratch), `downloads/<id>.zip`.
- `worker/lib/email.ts` (new) — `sendDownloadReadyEmail()`, a raw `fetch` call to Resend's REST API. No API key configured yet, so it logs `[email] ... would have emailed ...` instead of sending — confirmed this exact log line fired during testing.
- `worker/index.ts`'s `process-session` handler rewritten end to end: mark `processing` → look up the uploaded file and the owning user's email → `transcodeToMp4` → `extractSceneFrames` → write an honest placeholder `transcript.txt` (whisper.cpp isn't installed — say so, don't fake it) → zip everything → mark `complete` with `expires_at = NOW() + INTERVAL '1 hour'` → send/log the ready email → delete the upload and work directories either way (only the final zip survives, and only until claimed or expired). Failures update the session to `failed` with the real error message and re-throw so pg-boss also records the job itself as failed.
- **Caught and fixed a real bug while testing, not before**: `worker/lib/db.ts` built its `Pool` at module top-level from `process.env.DATABASE_URL`. That silently broke the moment `index.ts` actually imported it — ES module imports are hoisted, so `lib/db.ts`'s top-level code (including the `Pool` construction) ran *before* `index.ts`'s own `dotenv.config()` call populated `DATABASE_URL`, despite `config()` being textually first in the file. pg silently fell back to a default connection using the OS username as the database name (`FATAL: database "henrywalton" does not exist`). The old stub handler never hit this because it never imported `lib/db.ts` at all. Fixed by making `lib/db.ts` load its own env vars at its own top — the same self-contained pattern `index.ts` and `lib/migrate.ts` already use — rather than assuming an importing module has already done it.

### Download route + one-time enforcement

`GET /api/sessions/[id]/download` — auth-gated, ownership-checked. The real concurrency guard isn't a status check-then-act, it's an atomic `UPDATE sessions SET status = 'downloaded' ... WHERE status = 'complete' RETURNING id` — if two requests race for the same session, only one can possibly match that `WHERE` clause. Lazily flips overdue `complete` rows to `expired` (and deletes the file) at request time if the 1-hour window already passed, rather than relying on a scheduled sweep that doesn't exist. Serves the zip with a sanitized `Content-Disposition` filename, deletes it, done.

### Queue page, for real this time

`app/(app)/sessions/page.tsx` — finally scoped to `getCurrentUserId()` instead of listing every session in the database (a gap flagged since the auth work landed). Status badges for the full lifecycle, a Download button that appears only when `status = 'complete'`. `components/AutoRefresh.tsx` (new) — a client component that calls `router.refresh()` every 5 seconds so the queue updates without a manual reload; simple polling, not a websocket, since this isn't something users are expected to stare at live. Also fixed the dashboard's session-count widget, which was still doing a global `SELECT count(*) FROM sessions` — now scoped to the logged-in user too, since an unscoped count would've been actively misleading now that sessions are real per-user data.

## Email verification

Fleshing out account creation, scoped down to email verification specifically (asked which of a few directions mattered most — verification, form polish, or rate limiting — this was the pick).

**Design, settled before writing code**: soft/non-blocking. Signup still logs the user in immediately even unverified — a reminder banner is the whole enforcement, not a login gate. Nothing else (uploads, downloads) is gated on verification status either. Reasoning: the actual point of this is making sure notification emails reach a real inbox, not gatekeeping account access, and locking someone out of an account they just made over an unclickable link felt like the wrong tradeoff.

- **No new token table.** Verification links are short-lived (24h) JWTs signed with the same `SESSION_SECRET` sessions already use (`lib/auth.ts` → `createVerificationToken`/`verifyVerificationToken`) rather than a stored, looked-up token — nothing server-side to clean up, the signature + expiry + a `purpose` claim is the whole proof.
- **Purpose-scoping added to the existing session token too**, not just the new one — since both share a secret, `createSession`'s JWT now carries `purpose: "session"` and `getCurrentUserId()` checks for it explicitly. Without this, a verification-link token could have been replayed as a forged login session (or vice versa). Existing session cookies from before this change don't have the claim, so anyone already logged in got signed out — acceptable for local dev, worth knowing if this pattern gets copied into a context with real users already logged in.
- `lib/migrate.ts` — `ALTER TABLE users ADD COLUMN IF NOT EXISTS email_verified_at TIMESTAMPTZ`. `lib/seed.ts` — the dev account is now pre-verified (`email_verified_at = NOW()` on upsert), since `dev@screenscribe.test` is a non-routable address that could never click a real link — leaving it unverified would just make the banner nag forever in every local dev session for no reason.
- `lib/email.ts` (new, **root** package — the web app had no email sender before this, only the worker did, for a different purpose). Same raw-`fetch`-to-Resend pattern as `worker/lib/email.ts`, duplicated deliberately rather than shared.
- `GET /api/auth/verify` (no auth check — the token is the proof) and `POST /api/auth/resend-verification` (auth-gated). Signup now generates a token and sends the email after creating the session; a failed send doesn't fail signup, same non-fatal pattern as the worker's ready-email.
- `components/VerifyEmailBanner.tsx` (resend button, sending/sent/error states) rendered from `app/(app)/layout.tsx` whenever `email_verified_at IS NULL` — checked via one extra query in the layout, alongside the existing auth-gate query. Dashboard reads a `?verified=success`/`?verified=error` query param to show a confirmation or error message after the link redirect.
- **Hit a real Next.js gotcha while building the test harness**: a temporary route at `app/api/_test-only/verify-token/route.ts` (used to fetch a real token without inbox access, since there's no way to click a real email link in this environment) 404'd. Turns out any route folder starting with `_` is a Next.js *private folder* — excluded from routing entirely, not a naming convention I'd hit before. Renamed to `app/api/test-verify-token/` (no underscore) and it worked immediately. Deleted the whole route once testing was done — it was never meant to ship.
- **Verified end-to-end for real**: signed up with `admin@lightpatternsonline.com` (the only address the unverified Resend sender can currently reach) via a real browser, confirmed no Resend error in the server logs (the actual send succeeded — the code only logs on the no-op/error paths, so silence here is the success case), confirmed the banner appeared, confirmed the resend button works, fetched a real token via the temp route and hit the actual `/api/auth/verify` endpoint, confirmed `email_verified_at` got set, the banner disappeared, and the dashboard showed "Email verified — thanks!" Also confirmed a garbage token cleanly hits the error path. Cleaned up all test accounts and the temp route afterward.

Updated `CLAUDE.md` (new "Decided: email verification" section, auth-mechanism section's "not built" list trimmed, data model section), `docs/tech-stack/architecture.md` (new "Email verification" section), `database.md` (new column, no token table), and `api.md` (two new routes, the leading-underscore gotcha noted as a convention worth remembering).

## Fixed: browser autofill silently not filling controlled form fields

Reported: on the login form, autofilled email/password *looked* filled but the form acted like the field was empty unless a character was typed and deleted first — a "add and subtract a space" workaround. Asked to research it before touching code, since it had reportedly started happening on other sites too, not just here.

**Confirmed it's a known, documented React/browser interaction issue, not something specific to this codebase**: `LoginForm`/`SignupForm`'s email/password inputs were React-controlled (`value={state}` + `onChange`). Browser autofill sets an input's DOM value without reliably firing the native `input` event a controlled component's `onChange` depends on to update state — so the field visibly shows the autofilled value while React's internal state still thinks it's empty (or stale), and the *submitted* request uses the stale state, not what's on screen. Typing a real keystroke fires a genuine event and resyncs it, which is exactly what the space-then-delete trick was doing by hand.

**Fix**: stopped trusting React state for the submitted values entirely. Both forms are now uncontrolled (`defaultValue` instead of `value`, no `onChange`, `name` attributes added) and `handleSubmit` reads the actual values via `new FormData(e.currentTarget)` at submit time. This works regardless of *how* a value got into the field — typing, autofill, a password manager — because it's reading the DOM directly instead of asking React to have tracked it correctly.

**Verified against the real failure mode, not a proxy for it**: Playwright's `.fill()` simulates genuine typing (dispatches real input events), so it wouldn't have reproduced this bug at all. Instead, set the input's value via the native `HTMLInputElement` property setter directly, with zero events dispatched — the actual mechanism real autofill uses — then confirmed the network request to `/api/auth/login` still carried the correct values and login succeeded, using only what was in the DOM.

Updated `CLAUDE.md` (new bullet under "Decided: auth mechanism") and `docs/tech-stack/architecture.md`.

No DB changes.

## Post-signup email-sender message (blocked on domain verification) + phone number field

Asked for a post-signup message telling users to expect an email from `admin@lightpatternsonline.com`, plus phone number collection at signup.

**Caught a factual problem before building the message**: the real sender is `onboarding@resend.dev` (Resend's shared sandbox address) — `admin@lightpatternsonline.com` has only ever been the *recipient* used for testing (the Resend account owner's own inbox, the only address the sandbox sender can currently reach), never the sender. Shipping a message claiming otherwise would show users something that doesn't match what actually lands in their inbox. Asked how to resolve it rather than guessing; the answer was to properly verify `lightpatternsonline.com` with Resend (DNS records: MX, SPF TXT, DKIM TXT, typically on a `send.` subdomain) so it can genuinely send from `admin@lightpatternsonline.com` — this also fixes the standing sandbox limitation where mail can only reach the account owner, not real signups. Walked through the Resend-side steps; the DNS-provider side is blocked on the user actually adding the records (no access to their DNS). **The message and the `FROM_ADDRESS` change are both on hold until the domain shows verified in Resend** — not built yet, deliberately.

**Phone number collection — built, in parallel, since it doesn't depend on the domain work**:

- `lib/migrate.ts` — `ALTER TABLE users ADD COLUMN IF NOT EXISTS phone TEXT`, nullable.
- **Made it optional, not required** — a call, not something asked for explicitly either way. Requiring it at signup would sit oddly next to the "we don't hoard your data" pitch already on the hero page, and nothing currently uses the number (no SMS notifications built) to justify the friction of a mandatory field.
- `app/api/auth/signup/route.ts` — accepts an optional `phone`, validated only if provided (7–15 digits once punctuation is stripped, matching E.164's max length — not a specific country format, since phone formats vary too widely to assume one). Empty/omitted stores `NULL`.
- `components/SignupForm.tsx` — new "Phone number (optional)" field, `type="tel"`, read via the same `FormData`-at-submit pattern as the other fields (see the autofill fix earlier today).
- **Verified for real**: signed up with a formatted number (`(555) 123-4567`) — stored as typed; signed up with no phone — stored `NULL`, signup still succeeded; signed up with garbage (`abc12`) — rejected with a 400 and a clear message. Confirmed all three in the database directly, not just the HTTP status codes.

Updated `CLAUDE.md` and `docs/tech-stack/database.md` (`users` table description) to reflect the new column and that nothing reads it yet.

## Admin dashboard: users, token grants, and an honest revenue number

Asked for an admin-only tab to see users, revenue, and grant tokens to specific people. Paused on "revenue" first — no billing exists, so there was nothing real to show. Asked how to handle that rather than fabricating a number or shipping a fake-looking placeholder; the answer was to seed realistic test data into real infrastructure, so the feature actually works end to end, just against invented purchases instead of live ones.

**Schema** (`lib/migrate.ts`): `users.is_admin` (single boolean — one admin persona exists right now, not a team needing a real roles system) and `users.token_balance` (running total). `token_grants` is the actual ledger behind that balance: `tokens`, `amount_cents` (nullable — `NULL` means a comp/admin grant, set means a real-or-seeded purchase), `source`, `note`. The `amount_cents IS NOT NULL` distinction is what keeps "total revenue" from being inflated by free grants later.

**Seed data** (`lib/seed.ts`): the dev account is now also `is_admin = TRUE` (so local testing sees the tab without switching accounts), plus three fake demo customers — `alice@example.com` (a $15 subscription grant), `bob@example.com` (two pay-as-you-go purchases, $6 + $3), `carol@example.com` (a $0, comp `admin_grant` — deliberately included so the revenue-vs-comp distinction actually gets exercised, not just described). Re-seedable: wipes and recomputes a demo user's grants/balance each run instead of accumulating duplicates. Separately, `admin@lightpatternsonline.com` (the real account) was marked admin via a one-off `UPDATE`, not baked into the shared seed script — that's account-specific, not environment setup.

**Access control, checked twice**: `app/(app)/layout.tsx` now also fetches `is_admin` and passes it to `Sidebar`, which conditionally renders the "Admin" link — but that's UX only. `app/(app)/admin/page.tsx` and `POST /api/admin/grant-tokens` each independently re-check `is_admin` server-side, so hiding the link was never the actual security boundary.

**`app/(app)/admin/page.tsx`** — a revenue card (`SUM(amount_cents) WHERE amount_cents IS NOT NULL`, explicitly labeled "Seeded/test data — no live payment processor is connected yet") and a users table (email, phone, verified status, session count, per-user revenue, token balance, join date, an "Admin" badge where relevant) with a `GrantTokensForm` per row. `components/GrantTokensForm.tsx` posts to the new route and calls `router.refresh()` so the balance updates in place without a full reload.

**`POST /api/admin/grant-tokens`** — validates `tokens` is a positive integer, inserts the ledger row and increments the balance in one transaction (`BEGIN`/`COMMIT`, rolls back if the target user doesn't exist).

**Verified end-to-end with a real browser, all 11 checks**, not just that pages loaded: logged in as admin, confirmed the Admin link appears and `/admin` shows exactly `$24.00` (the real sum of the seeded grants — $15 + $6 + $3, carol's comp excluded, not just "some number rendered"), confirmed all three demo emails appear, granted 25 tokens to alice through the actual form and confirmed her balance went from 100 to 125 both on screen and directly in the database. Then, separately, signed up a fresh non-admin account and confirmed all three angles of the gate: no Admin link shown, redirected away from `/admin` on direct navigation, and a real `403` hitting the grant-tokens API directly (not relying on the link being hidden).

Updated `CLAUDE.md` (new "Decided: admin dashboard" section, business-model section's stale "no token_balance column exists" claim corrected, data model section), `docs/tech-stack/database.md` (`token_grants` table, `users` additions), and `api.md` (new route).

No DB changes beyond the migration already covered above.
