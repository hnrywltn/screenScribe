# Changes — August 14, 2026

## Building the upload flow: drag-and-drop, queue, notifications

Big feature — the actual upload → process → download path, not just infrastructure around it. Before writing code, settled two open design questions:

- **Notifications: email + in-app.** A 30–60 minute processing job means a user realistically walks away and comes back later, not watches a progress bar — email is the primary channel, the queue page shows live status for when they are in the app.
- **Download window: 1 hour.** Async job processing (already decided) put the "ephemeral, nothing kept around" storage promise in tension with reality — the finished file has to sit *somewhere* between "job done" and "user downloads it." Settled on a hard 1-hour expiry: matches a "process it, then go grab it" usage pattern, keeps the privacy promise meaningfully tight rather than "ephemeral" quietly becoming "kept around indefinitely." After expiry the file's gone — re-processing (and spending tokens again, once billing exists) is required.

**Two scope calls made explicit up front, not papered over:**
- **Local dev uses a shared temp directory** (`SHARED_TEMP_DIR`) between the web app and worker, since they're the same machine here. Production (separate Railway services, no shared filesystem) needs the real network-based handoff already decided but never built — flagged clearly as a gap, not pretended to be solved.
- **Resend** chosen for email (simple REST API, no SDK needed) — but there's no real API key configured, so sends will log instead of actually going out until one exists.
- **Uploads are unmetered for now** — token/billing enforcement isn't built, so this doesn't try to wire it in as a side effect of building the upload flow.

### Schema

`lib/migrate.ts` — first real `ALTER` on `sessions` rather than a from-scratch rewrite (real user accounts exist now, not just empty tables): `status` default changed to `queued`, added `expires_at TIMESTAMPTZ` for the download window. New lifecycle: `queued` → `processing` → `complete` → `downloaded`, or → `expired`/`failed`. Ran and re-ran to confirm idempotency.

### Job enqueueing from the web app

The web app previously had no way to create pg-boss jobs — only the worker did. Added `pg-boss` to the root `package.json` and `lib/queue.ts` (`sendProcessSessionJob(sessionId)`), a singleton client that lazily starts and idempotently ensures the `process-session` queue exists before sending, so it doesn't depend on the worker having started first.

### Upload UI

`components/UploadDropzone.tsx` — drag-and-drop or click-to-browse, client-side video-type/2GB size check before ever touching the network. Uses `XMLHttpRequest` instead of `fetch` specifically for its `upload.progress` event — a multi-hundred-MB video is exactly the case where a bare spinner isn't good enough feedback. Wired into `app/(app)/upload/page.tsx`, replacing the old "Coming soon" stub.

### Upload API route

`POST /api/sessions` — auth-gated, re-validates file type/size server-side (never trust the client check alone), inserts the `sessions` row first to get a real id, then writes the raw file to `SHARED_TEMP_DIR/uploads/<id>/` and enqueues the job. If anything fails after the row's created (disk write, enqueue), the session gets marked `failed` with a message rather than sitting stuck in `queued` forever with no explanation. Accepted the buffer-whole-file-in-memory tradeoff rather than building a streaming multipart parser — flagged as a real limitation for later, not hidden.

This is the part that actually does the work now, not a stub that logs receipt.

- Added `archiver` to the worker package for zip packaging. Checked its actual README before writing code rather than assuming the API from memory — good thing: the installed v8 uses a class-based API (`new ZipArchive(...)`), not the older `archiver('zip', opts)` factory function pattern.
- `worker/lib/tempStorage.ts` (new, worker-side duplicate of the web app's own copy — separate packages, no shared import) — the filesystem convention both sides agree on: `uploads/<id>/`, `work/<id>/` (worker-only scratch), `downloads/<id>.zip`.

### Download route + one-time enforcement

`GET /api/sessions/[id]/download` — auth-gated, ownership-checked. The real concurrency guard isn't a status check-then-act, it's an atomic `UPDATE sessions SET status = 'downloaded' ... WHERE status = 'complete' RETURNING id` — if two requests race for the same session, only one can possibly match that `WHERE` clause. Lazily flips overdue `complete` rows to `expired` (and deletes the file) at request time if the 1-hour window already passed, rather than relying on a scheduled sweep that doesn't exist. Serves the zip with a sanitized `Content-Disposition` filename, deletes it, done.

## Email verification

Fleshing out account creation, scoped down to email verification specifically (asked which of a few directions mattered most — verification, form polish, or rate limiting — this was the pick).

**Design, settled before writing code**: soft/non-blocking. Signup still logs the user in immediately even unverified — a reminder banner is the whole enforcement, not a login gate. Nothing else (uploads, downloads) is gated on verification status either. Reasoning: the actual point of this is making sure notification emails reach a real inbox, not gatekeeping account access, and locking someone out of an account they just made over an unclickable link felt like the wrong tradeoff.

Existing session cookies from before this change don't have the claim, so anyone already logged in got signed out — acceptable for local dev, worth knowing if this pattern gets copied into a context with real users already logged in.

## Fixed: browser autofill silently not filling controlled form fields

Reported: on the login form, autofilled email/password *looked* filled but the form acted like the field was empty unless a character was typed and deleted first — a "add and subtract a space" workaround. Asked to research it before touching code, since it had reportedly started happening on other sites too, not just here.

**Confirmed it's a known, documented React/browser interaction issue, not something specific to this codebase**: `LoginForm`/`SignupForm`'s email/password inputs were React-controlled (`value={state}` + `onChange`). Browser autofill sets an input's DOM value without reliably firing the native `input` event a controlled component's `onChange` depends on to update state — so the field visibly shows the autofilled value while React's internal state still thinks it's empty (or stale), and the *submitted* request uses the stale state, not what's on screen. Typing a real keystroke fires a genuine event and resyncs it, which is exactly what the space-then-delete trick was doing by hand.

**Fix**: stopped trusting React state for the submitted values entirely. Both forms are now uncontrolled (`defaultValue` instead of `value`, no `onChange`, `name` attributes added) and `handleSubmit` reads the actual values via `new FormData(e.currentTarget)` at submit time. This works regardless of *how* a value got into the field — typing, autofill, a password manager — because it's reading the DOM directly instead of asking React to have tracked it correctly.

**Verified against the real failure mode, not a proxy for it**: Playwright's `.fill()` simulates genuine typing (dispatches real input events), so it wouldn't have reproduced this bug at all. Instead, set the input's value via the native `HTMLInputElement` property setter directly, with zero events dispatched — the actual mechanism real autofill uses — then confirmed the network request to `/api/auth/login` still carried the correct values and login succeeded, using only what was in the DOM.

Updated `CLAUDE.md` (new bullet under "Decided: auth mechanism") and `docs/tech-stack/architecture.md`.

No DB changes.

## Admin can pause or revoke a user's account

Asked for the ability to pause or revoke a user from the admin page.

**Schema** (`lib/migrate.ts`): `users.account_status TEXT NOT NULL DEFAULT 'active'` (`'active'`/`'paused'`/`'revoked'`). Plain TEXT with no DB `CHECK` constraint, same convention already used for `sessions.status` — validity is enforced at the app layer instead.

**The real design problem this required solving**: sessions are stateless signed JWTs (see "Decided: auth mechanism" earlier this session) — there's no server-side session store to invalidate, so flipping a DB column alone wouldn't do anything to someone already logged in with a valid cookie. Fixed by moving the enforcement point into `getCurrentUserId()` (`lib/auth.ts`) itself, which every protected route and page already calls on every single request. It now verifies the JWT as before, but then also queries the user's current `account_status` from the database and returns `null` (treated identically to "not logged in") unless it's `'active'`. No new architecture needed — just extending a choke point that already existed. The tradeoff, accepted deliberately: one extra DB query per request instead of a free JWT-only check; not a concern at this scale.

- `app/api/auth/login/route.ts` — checks `account_status` *after* password verification succeeds, not before, and returns a specific message ("Your account has been paused. Contact support for help." / "Your account has been revoked.") rather than the generic invalid-credentials message. Ordering matters here for the same user-enumeration reason the generic message exists at all: revealing "this account is paused" to someone who hasn't actually proven they know the password would itself leak account-status information.
- **A pause is not a logout** — the session cookie itself is never touched or deleted. While paused, the existing cookie is simply rejected by the live status check on every request; if reactivated, the original session resumes working immediately with no re-login required, since the cookie was valid the whole time.
- `POST /api/admin/set-account-status` (new route) — admin-gated the same independent way as `grant-tokens`, body `{ userId, status }` validated against the three allowed values, and refuses with a 400 if `userId` matches the calling admin's own id — a guard against an admin accidentally locking themselves out with no other admin around to undo it.
- `components/AccountStatusControl.tsx` (new) — a colored status dot (green/amber/red) plus a `<select>` per row on the admin users table, posts to the new route and calls `router.refresh()`. Renders as a disabled read-only label (no dropdown) on the admin's own row, matching the API's self-lockout guard rather than just failing silently if they tried.
- `app/(app)/admin/page.tsx` — new "Status" column using the control above.

**Verified end-to-end with two simultaneous real browser sessions**, not just the API in isolation: logged in as bob in one browser context, then as admin in a second context, paused bob from the admin UI — his *already-open* tab was bounced straight to `/login` on its very next request, with no action taken in that tab itself. ## Upload-time token enforcement (with grace debt), paid expiry extension + real cleanup sweep, auth hardening

Three follow-ups on gaps flagged in the last update: uploads were still unmetered, expiry cleanup was lazy-only, and auth had no rate limiting or password reset. Planned all three together before writing code, since they touch shared infrastructure (the ledger, the worker's job handling, pg-boss scheduling). Key decisions going in: token debt allowed down to **-100** rather than a hard block on upload (a shortage shouldn't stop someone from processing a video they already recorded — it gets paid off by their next purchase); expiry extension capped at **one use per session** (max 2 hours total) rather than unlimited; a **real** pg-boss-scheduled cleanup sweep, not lazy-only.

**A design-review pass caught three real bugs before any code was written** — worth calling out specifically since they weren't obvious from the individual pieces in isolation:
1. **Double-refund risk.** pg-boss defaults to `retryLimit: 2`. `processSession()` isn't written to be safely re-entrant (unconditionally marks `processing` at the top, no check of current status) — a retried failed job would have found the same charge and refunded it twice.
2. **Unrefunded-charge gap.** If a charge succeeded but enqueueing the job itself then failed, the worker would never run and never refund — money taken, nothing given back, since only the worker's catch block was originally going to handle refunds.
3. **Rate-limit enumeration hole.** Recording failed-login attempts only on wrong-password (not on no-such-user) would let an attacker distinguish real accounts from fake ones by watching for the 429 — reopening exactly the hole the generic "Invalid email or password" message exists to close.

All three are fixed in what shipped, not left as known issues.

### Token enforcement

- **`lib/ffprobe.ts`** (new) — `probeDurationSeconds()` shells to `ffprobe` (captures **stdout**, unlike `worker/lib/ffmpeg.ts`'s `runFfmpeg` which captures stderr — ffprobe's actual output goes to stdout). Runs in the **web app**, a genuinely new production gap: the web app's own container now also needs `ffprobe` installed, beyond the already-documented "worker needs ffmpeg on Railway" gap.
- **`lib/tokens.ts`** (new) — `chargeTokens()`: one atomic `UPDATE users SET token_balance = token_balance - $cost WHERE ... AND token_balance - $cost >= -100 RETURNING token_balance` (not read-then-write, so Postgres's row locking — not application code — prevents two concurrent charges from jointly crossing the floor), paired with a `token_grants` insert (`tokens` stored negative, `source = 'usage_upload'`/`'usage_extend'`, `session_id` set) to keep the existing "every balance change has a ledger row" invariant intact. `refundUsageCharge()`: idempotency-guarded (checks for an existing `'refund'` row before crediting) — this guard is what makes bug #1 safe to fix defensively even beyond the `retryLimit: 0` fix below.
- `app/api/sessions/route.ts` — after writing the file, probes duration, charges `Math.max(1, Math.ceil(seconds / 60))` tokens. Insufficient (even with debt) → session marked `failed` with the exact shortfall ("you need N more"), file deleted, nothing charged, job never enqueued. If enqueueing itself then fails, the existing catch block now also calls `refundUsageCharge` — this is bug #2's fix.
- `worker/index.ts` — `process-session`'s queue now has `retryLimit: 0` explicitly (`createQueue` + a one-time `updateQueue` fixup, since the queue already existed with the old default) — bug #1's fix at the source. The job-failure catch block also calls `refundUsageCharge` before re-throwing.
- `worker/lib/tokens.ts` (new) — duplicates `refundUsageCharge` only (the worker never charges) — same cross-package duplication pattern already used for `email.ts`/`tempStorage.ts`.
- **Schema**: `token_grants.session_id` (nullable FK → `sessions`, `ON DELETE SET NULL`), indexed.

### Expiry extension + real scheduled cleanup

- `POST /api/sessions/[id]/extend` (new) — one transaction: an atomic conditional `UPDATE sessions SET expires_at = expires_at + INTERVAL '1 hour', extended = TRUE WHERE ... AND extended = FALSE AND expires_at > NOW()` (0 rows covers already-extended/expired/wrong-status/not-yours in one shot), then `chargeTokens()` for 50 tokens. A failed charge rolls back the whole transaction — including the `expires_at` bump, since nothing had committed yet.
- **Schema**: `sessions.extended BOOLEAN NOT NULL DEFAULT FALSE`.
- `worker/index.ts` — a second queue, `cleanup-expired-sessions`, registered via `createQueue` + `schedule('*/15 * * * *')` + `work(...)` alongside the existing `process-session` setup (keeping the existing "`.work()` only lives in the worker" convention intact). Handler: finds `complete` sessions past `expires_at`, deletes the zip, flips status to `expired`. Left at pg-boss's default `retryLimit` (unlike `process-session`) — this handler is naturally idempotent (conditional `UPDATE`, force-`rm`), so a retry on a transient failure is harmless. Also prunes `rate_limit_attempts` rows older than 24h in the same pass — cheap to fold in since the scheduling infrastructure now exists.
- The download route's original lazy expiry check is unchanged — now a backstop for the window between real expiry and the next 15-minute sweep, not the sole mechanism.
- `app/(app)/sessions/page.tsx` + `components/ExtendSessionButton.tsx` (new) — an "Extend (+50 tokens)" button next to Download whenever a session is `complete` and not yet extended, plus a small "Ready — download by ..." expiry line.

### Auth hardening: rate limiting + password reset

- **`rate_limit_attempts` + `lib/rateLimit.ts`** (new) — Postgres-backed, not Redis, same reasoning as choosing `pg-boss` over new queue infra. `isRateLimited(key, action, maxAttempts, windowMinutes)` (windowed `COUNT(*)`), `recordAttempt(key, action)`.
- **Login**: 5 failed attempts / 15 minutes, keyed by email, checked *before* the `SELECT ... FROM users`. Recorded on **both** failure branches (no-such-user and wrong-password) — the enumeration fix from bug #3.
- **Signup**: 10 signups / hour, keyed by client IP (`x-forwarded-for`, best-effort).
- **Forgot-password**: 5 / 15 minutes, keyed by email.
- **Password reset**, mirroring email verification's existing pattern (no DB token table, a purpose-scoped stateless JWT): `lib/auth.ts` gains `createPasswordResetToken`/`verifyPasswordResetToken` (`purpose: "password-reset"`, 30-minute expiry — shorter than verification's 24h, since replaying a reset link isn't harmless the way replaying a verification link is). `lib/email.ts` gains `sendPasswordResetEmail`. `POST /api/auth/forgot-password` (new) always returns `{ok:true}` regardless of whether the email exists. `POST /api/auth/reset-password` (new) verifies the token, updates `password_hash`, and clears any existing login lockout for that email — otherwise someone who just proved account ownership via email could still be locked out from their own earlier failed guesses. New pages `app/(marketing)/forgot-password` and `.../reset-password` (+ `ForgotPasswordForm`/`ResetPasswordForm`) deliberately skip the "redirect if already logged in" guard login/signup have — a user logged in on one device can legitimately need to reset a password from another. Both forms use the established uncontrolled-input/`FormData` pattern from `LoginForm.tsx`. Added a "Forgot password?" link to the login form.
- **Known, accepted trade-offs, documented not fixed**: reset tokens have no single-use tracking (same trade-off already accepted for verification links) and resetting a password doesn't invalidate other already-active sessions (sessions are pure stateless JWTs unrelated to `password_hash`) — structurally the same problem `account_status` solved for pause/revoke, cheap to close the same way later if needed.

Balance at -95 with the same video → succeeded (debt allowed). **Forced a real worker failure** (temporarily renamed the `ffmpeg` binary off `PATH`) → exactly one refund row, balance restored; directly re-invoked the refund logic a second time on the same session → the idempotency guard no-op'd it, proving bug #1's fix for real, not just by reasoning about `retryLimit`. **Forced a failure between charging and enqueueing** (temporarily made `sendProcessSessionJob` throw, reverted immediately after) → the upload route's own catch block refunded correctly, proving bug #2's fix.

## Session invalidation on password change

A known gap flagged in the last update — a password reset didn't invalidate the user's other already-active sessions elsewhere, since sessions are stateless JWTs unrelated to `password_hash`. Asked to close it, and the fix was already sketched in `CLAUDE.md`'s own notes: `users.password_changed_at` (nullable, set on every successful reset), compared against a session JWT's own `iat` claim inside `getCurrentUserId()` — the exact same live-invalidation choke point `account_status` already uses for pause/revoke, just keyed on a timestamp instead of a status flag. Any session issued before the most recent password change gets rejected on its very next request.

`app/api/auth/reset-password/route.ts` now sets `password_changed_at = NOW()` alongside the `password_hash` update.

**Verified with two simultaneous browser contexts**, the same technique used for the original pause/revoke verification: logged in and kept a session open in one context, reset the password from a completely separate, unauthenticated context, and confirmed the original still-open session got bounced straight to `/login` on its next navigation — with zero action taken in that tab itself. Confirmed a fresh login with the new password works normally afterward.

Updated `CLAUDE.md` (folded into the existing "Decided: rate limiting & password reset" section, replacing the old "known gap" note) and `docs/tech-stack/database.md` (`users.password_changed_at`).

## Download streaming (upload streaming discussed, deliberately deferred)

Asked to discuss the "streaming upload/download" gap before building anything. Broke it into two genuinely different problems: download streaming is a small, low-risk, server-only change (swap `readFile()`+`Buffer` for a piped stream); upload streaming is bigger, since Next.js's `request.formData()` already buffers the entire multipart body internally before the route handler ever sees it — fixing that means switching the upload transport away from multipart entirely (a raw-body stream, filename passed via a header instead of a form field), touching both the route and `UploadDropzone.tsx`. Recommended doing download now and deferring upload; agreed.

**`app/api/sessions/[id]/download/route.ts`** — replaced `readFile()`+`Buffer` with `createReadStream()` piped through Node's `Readable.toWeb()`, so a multi-hundred-MB zip is no longer held whole in server memory to serve it. Uses `stat()` instead of `readFile()` for the missing-file check (and to populate a real `Content-Length` header, which streaming responses don't get automatically). **Deletes the file immediately after opening the read stream**, not after the client finishes downloading — a deliberate choice, not an oversight: on POSIX (both this Mac and the Linux Railway target), an open file descriptor keeps the underlying data readable until the descriptor itself closes, even after the directory entry is removed, so unlinking early doesn't corrupt an in-flight read. This also tightens the one-time-download promise slightly — the file is gone from disk the moment the response starts, not only once the client finishes.

**Verified for real, not just by reasoning about POSIX semantics**: uploaded and processed a real test video, downloaded it, confirmed via `ls` that the file was already gone from disk by the time response headers came back (before the client had even finished reading the body), confirmed the downloaded zip passed `unzip -t` with zero errors and all three expected files (`video.mp4`, a screenshot, `transcript.txt`) present and valid, confirmed `Content-Length` matched the actual byte count exactly, and confirmed the existing one-time-download enforcement still holds (a second download attempt correctly returns 410).

Updated `CLAUDE.md` ("Decided: notifications & download window" section, "deliberately not built yet" list split into "upload streaming, still not built" vs. "download streaming, fixed") and `docs/tech-stack/api.md` (download route row).
